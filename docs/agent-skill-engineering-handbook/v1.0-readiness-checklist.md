# v1.0 Readiness Checklist

本文件不是第十章，而是 Agent Skill Engineering Handbook 进入 v1.0 前的发布门槛。它用来确认：九章主线、附录、引用规范、审计结果和方法论边界是否已经闭合。

## 本文件证据底座

这份 checklist 继承手册前九章的核心判断：Skill 的最小可交付形态是 `SKILL.md`，但成熟度可以沿着 references、scripts、evals、governance 和 lifecycle 逐步增强；这种判断来自 Agent Skills spec 对 `SKILL.md` 与可选资源的定义、Anthropic 对 progressive disclosure 和资源组织的建议、OpenAI 对 Skills / Plugins 的产品化说明，以及 Microsoft / AWS 对 agent 能力治理、评估和可观测性的工程实践。[Agent Skills Spec][agent-skills-spec] [Anthropic Best Practices][anthropic-best-practices] [OpenAI Skills][openai-skills] [OpenAI Plugins][openai-plugins] [Microsoft Agent Skills][microsoft-agent-skills] [AWS Evaluations][aws-evaluations] [AWS Observability][aws-observability]

本文件只检查“是否足以形成 v1.0”，不引入新的 Skill 分类，也不改变前文的边界句：Skill teaches; resources ground; scripts assist; tools act; workflows govern; platforms operate。该边界句是本教程的综合方法论，而不是某个厂商的官方术语。[Chapter 5][chapter-5] [Chapter 7][chapter-7]

## 1. Scope Gate

v1.0 应该回答一个清晰问题：如何在 2026 年的大模型生态中，设计、编写、验证、治理和维护一个可复用的 agent skill。它不应该变成某个具体项目的复盘、厂商新闻汇编，或个人工作流教程。[README][handbook-readme] [Chapter 1][chapter-1]

- [ ] 九章内容均围绕 Skill 开发方法论，而不是具体业务系统。
- [ ] 所有项目经验只作为抽象方法论来源，不暴露项目业务痕迹。
- [ ] “Local-First, Cloud-Assisted”“Dual Presence”“Self-Contained Bundling”等判断都被放在 Skill 工程边界内解释，而不是被包装成未经来源支持的行业口号。[Chapter 1][chapter-1] [Chapter 5][chapter-5]
- [ ] 厂商资料用于支撑方法论，不以厂商对照表作为教程主结构。

状态：`Pass / Needs Work / Blocked`

## 2. Structure Gate

v1.0 的主线应该已经从认知、触发、正文、资源、执行边界、评估、安全、生命周期走到完整构建案例。这个顺序和 Agent Skills spec / Anthropic / OpenAI 对 Skill 结构的共同趋势一致：先定义最小结构，再用 progressive disclosure、可执行辅助、评估和治理提升成熟度。[Agent Skills Spec][agent-skills-spec] [Anthropic Best Practices][anthropic-best-practices] [OpenAI Skills][openai-skills]

- [ ] 第一章解释 Skill 的现代定位、双重身份和轻量包 / 工程化 bundle 的区别。[Chapter 1][chapter-1]
- [ ] 第二章解释 activation / description 为什么先于正文指令。[Chapter 2][chapter-2]
- [ ] 第三章解释 `SKILL.md` body 如何写成被触发后的操作程序。[Chapter 3][chapter-3]
- [ ] 第四章解释 references / assets / scripts / evals 如何按需组织。[Chapter 4][chapter-4]
- [ ] 第五章解释 scripts / tools / MCP / workflow / plugin 的边界。[Chapter 5][chapter-5]
- [ ] 第六章解释 evaluation 和 forward testing 如何建立可信度。[Chapter 6][chapter-6]
- [ ] 第七章解释安全、权限、审计和治理。[Chapter 7][chapter-7]
- [ ] 第八章解释版本、维护、退役和分发生命周期。[Chapter 8][chapter-8]
- [ ] 第九章把前八章收束为一个 pro-level skill 构建案例。[Chapter 9][chapter-9]

状态：`Pass / Needs Work / Blocked`

## 3. Citation Gate

每章关键观点应在正文中给出可点击 Markdown 引用，并在章末集中列出 `## Sources`。这条规则来自本项目全局写作规范，也符合教程需要把“综合判断”和“官方来源”区分开的要求。[Tutorial Writing Guidelines][tutorial-writing-guidelines]

- [ ] 每个章节和附录都有 `## Sources`。
- [ ] 关键判断、引用句、厂商实践和规范性说法都带正文引用。
- [ ] 引用优先使用官方文档、标准规范、平台文档或一手资料。
- [ ] 多来源综合结论明确标注为“教程综合 / 方法论归纳”，不伪装成厂商标准术语。
- [ ] 所有正文引用 id 都能在同文件底部找到定义。

状态：`Pass / Needs Work / Blocked`

## 4. Methodology Consistency Gate

v1.0 不应出现彼此冲突的 Skill 观。尤其要保持两点稳定：轻量 Skill 可以是专业形态，工程化 bundle 也是专业形态；二者差异来自风险、复用频率、确定性要求、分发和治理，而不是目录数量本身。[Chapter 1][chapter-1] [Chapter 4][chapter-4] [Appendix B][appendix-b]

- [ ] 没有把 `scripts/`、`assets/`、`evals/` 写成所有 Skill 的必选项。
- [ ] 没有把 `SKILL.md` 当成普通 README 或长篇知识库。
- [ ] 没有把 MCP / tool / plugin / workflow 混写成 Skill 的同义词。
- [ ] 没有把个人 research/spec 流程写成 Skill 行业通用流程。
- [ ] 第九章案例遵循前八章边界，没有额外发明新分类。

状态：`Pass / Needs Work / Blocked`

## 5. Appendix Gate

附录应该服务于写作和审查，而不是扩充理论。模板、目录形态、触发测试、评估测试和安全发布检查这五类附录，分别对应前文的写作、结构、activation、evaluation 和 governance 主题。[Appendix A][appendix-a] [Appendix B][appendix-b] [Appendix C][appendix-c] [Appendix D][appendix-d] [Appendix E][appendix-e]

- [ ] Appendix A 可直接用于起草 `SKILL.md`。
- [ ] Appendix B 可帮助判断轻量 Skill / bundle / package / plugin 的取舍。
- [ ] Appendix C 可检查 `description` 的触发质量和误触发风险。
- [ ] Appendix D 可做 fresh-agent forward testing 和回归夹具设计。
- [ ] Appendix E 可做安全、权限、发布和回滚检查。

状态：`Pass / Needs Work / Blocked`

## 6. Audit Gate

v1.0 发布前至少应完成两类审计：全手册一致性审计，以及附录专项审计。现有审计记录显示，前九章、README、Appendix A 以及 Appendix C/D/E 已做过一致性、引用和边界检查，并修复了已发现的问题。[Full Handbook Audit][full-audit] [Appendix Audit][appendix-audit]

- [ ] 全手册审计文件存在，并记录问题、修复和结论。
- [ ] 附录专项审计文件存在，并记录问题、修复和结论。
- [ ] 审计结果没有未关闭的高优先级问题。
- [ ] 新增文件通过引用闭合检查。
- [ ] 新增文件通过项目业务痕迹检查。

状态：`Pass / Needs Work / Blocked`

## 7. Release Decision

当上面六个 gate 都达到 `Pass` 时，可以把当前版本标记为 v1.0 draft 或 v1.0 internal release。若只剩风格润色、章节标题微调、示例语言优化，这些属于 v1.0 之后的编辑工作，不应阻塞第一版方法论成形。

推荐发布结论：

- [ ] `Ready for v1.0 draft`：结构完整，引用闭合，无已知方法论冲突。
- [ ] `Ready after minor edits`：只有局部表述、错别字或链接标题需要修正。
- [ ] `Not ready`：存在章节缺失、关键引用缺失、概念冲突或业务痕迹泄漏。

状态：`Pass / Needs Work / Blocked`
