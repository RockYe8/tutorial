# 01 - 从 Todo MVP 理解 Codex Skills

这篇是给第一次接触 Codex Skills 的开发者看的。你不需要先理解整套工程流程，也不需要先写一个复杂应用。我们只用一个很普通的个人 Todo MVP：添加任务、完成任务、看今天要做什么。

重点不是 Todo App 本身，而是观察一件事：当你把“我想做个 Todo App”丢给 AI 时，普通 prompt 往往会让它太快开始写代码；Skills 会先把“该怎样工作”固定下来，让 agent 用一套可重复的流程推进。

Matt Pocock 在 [AI Hero Skills Catalog](https://www.aihero.dev/skills-catalog) 里把 Skill 描述成一种 focused, repeatable workflow；[`mattpocock/skills`](https://github.com/mattpocock/skills) 这个仓库也把它们放在“真实工程纪律”里理解，而不是把它们当成一串神奇咒语。这个心智模型很重要：Skill 不是“更长的 prompt”，而是“下次遇到同类问题时，agent 应该重复执行的工作方式”。

<a id="skills-as-workflows"></a>
## Skills 是可复用工作流，不是魔法 prompt

普通 prompt 常常长这样：

```text
帮我做一个 Todo App，用 React，界面好看一点。
```

这个请求看起来清楚，其实里面有很多空白：

- Todo 是给一个人用，还是团队用？
- MVP 是否需要登录？
- 任务是否需要截止日期？
- “今天要做什么”是一个筛选条件，还是一个单独视图？
- 数据先存在浏览器本地，还是马上接后端？
- 你更关心学习 React，还是真的想尽快有一个可用工具？

如果 agent 立刻开始实现，它只能猜。猜对时你会觉得它很聪明；猜错时，你会得到一堆“看起来完整、但方向不对”的代码。

Skill 改变的是这个起手式。你不是说“现在写代码”，而是说“请进入某个工作流”。比如：

```text
/grill-me

我想做一个个人 Todo MVP，但范围还很模糊。请先把我问清楚，不要急着写方案。
```

这时你调用的不是某段魔法 prompt，而是一套行为约束：先追问、找边界、拆决策、暴露风险、最后再总结下一步。它的价值在于可重复。下次你想做读书笔记、习惯追踪器、博客后台，也可以用同样方式先把想法问清楚。

一个好用的心智模型是：

| 普通 prompt | Skill |
| --- | --- |
| “请给我答案” | “请按这套流程工作” |
| 依赖 agent 现场发挥 | 依赖可重复的步骤 |
| 容易过早实现 | 先确认目标、边界和验收 |
| 结果常常是一次性的 | 结果能沉淀成 spec、ticket、handoff 或学习记录 |

<a id="grill-me"></a>
## 用 `/grill-me` 把模糊想法问清楚

当你只有一个模糊想法时，先用 `/grill-me`。它适合还没有进入真实仓库、还没有共享领域文档、只是想把脑子里的东西说清楚的阶段。

你可以这样开始：

```text
/grill-me

我想做一个个人 Todo MVP。目标是每天打开就知道今天要做什么。
我还不确定要不要截止日期、标签、登录和后端。请先问我问题。
```

一个真实可模仿的短对话可能是这样：

```text
Codex: 这个 MVP 的第一成功标准是什么？是“能记录任务”，还是“每天帮你决定优先级”？
你: 第一版只要记录任务和今天视图，不做智能优先级。

Codex: 任务需要跨设备同步吗？这个决定会直接影响是否需要后端。
你: 不需要。先存在浏览器本地。

Codex: “今天视图”里的任务从哪里来？手动标记为今天，还是根据截止日期自动出现？
你: 手动标记为今天。截止日期先不做。

Codex: 完成任务后是隐藏、划掉，还是进入完成列表？
你: 今天视图里隐藏，全部任务里保留完成状态。
```

注意这个对话没有急着产出组件、数据库表或路由。它先把 MVP 的形状压小：

- 单用户。
- 无登录。
- 无后端。
- 本地存储。
- 三个核心动作：添加任务、标记今天、完成任务。
- 两个核心视图：今天、全部。

这就是 `/grill-me` 的意义：把“做个 Todo App”变成“做一个本地优先、手动 Today 标记、两视图的个人 Todo MVP”。后者才适合继续写 spec 或直接做一个小原型。

什么时候 `/grill-me` 就够了？

如果你还在想产品方向、学习目标、个人工具范围，或者这件事还没有绑定到具体仓库，`/grill-me` 足够。它帮助你思考，不强迫你创建工程文档。

什么时候应该升级到 `/grill-with-docs`？

当你已经在真实仓库里工作，并且这些讨论会影响代码命名、领域术语、ADR 或后续 tickets 时，就该换成 `/grill-with-docs`。比如第二篇会继续这个 Todo 例子：已有应用要加入标签、筛选和归档，这时“任务”“标签”“归档”的含义需要进入仓库文档，而不只是留在聊天里。

<a id="grilling"></a>
## `/grilling` 是追问背后的工作纪律

`/grill-me` 是你可以直接输入的 Skill；`/grilling` 更像底层纪律。你可以把它理解成：任何认真澄清需求的流程，都应该有一套追问方法，而不是随便问几个问题就结束。

在 Todo MVP 里，普通的追问可能只问：

```text
你想要哪些功能？
```

`/grilling` 背后的追问更接近：

```text
Codex: 如果只能保留一个能力，这个 Todo MVP 必须解决什么问题？
Codex: 哪些功能听起来常见，但第一版明确不要？
Codex: 哪个决定一旦做错，会让后面返工最多？
Codex: 你打算怎么判断第一版已经够用了？
```

这类问题会逼出边界。比如：

- “标签”不是第一版必须。
- “截止日期”会让 today 逻辑变复杂，先不做。
- “本地存储”比“账号系统”更符合个人 MVP。
- “能连续三天真实记录自己的任务”比“功能列表很长”更像验收标准。

所以，当你看到 `/grill-me` 或 `/grill-with-docs` 一直问问题，不要急着把它当成拖慢速度。它是在保护你免于更慢的返工。

<a id="ask-matt"></a>
## 用 `/ask-matt` 选择下一步

新手很容易卡在“我知道有很多 Skills，但不知道现在该用哪个”。这时不要猜，直接用 `/ask-matt`。

你可以这样说：

```text
/ask-matt

我刚用 /grill-me 把个人 Todo MVP 问清楚了。
现在我有一段清晰对话，但还没有进入仓库。
我应该继续写 spec、做 prototype，还是直接实现？
```

一个短对话可能是：

```text
Codex: 你现在最想降低哪类风险：需求不清、交互手感不确定，还是实现工作量不确定？
你: 交互手感。我不确定 today 视图和全部视图怎么切换最舒服。

Codex: 那下一步更像 /prototype，而不是 /to-spec。
先用一个低成本原型回答视图切换问题，再把确认过的行为写进 spec。
```

`/ask-matt` 的价值不是替你做决定，而是帮你选择流程。你只要描述当前材料和卡点，它会把你路由到更合适的 Skill。

对初学者来说，可以记住这条经验：

- 想法模糊：先 `/grill-me`。
- 不知道用哪个 Skill：问 `/ask-matt`。
- 已经进入真实仓库并会影响长期语言：用 `/grill-with-docs`。
- 会话太长，需要交接：用 `/handoff`。
- 想把仓库当学习环境：用 `/teach`。

<a id="handoff"></a>
## 用 `/handoff` 保存上下文

AI 编程里一个常见问题是：前面聊了很多，后面会话变长、换任务、换 agent，关键上下文散掉了。

对 Todo MVP 来说，你可能已经通过 `/grill-me` 明确了这些决定：

- 第一版无登录、无后端。
- 任务存在本地。
- Today 是手动标记，不来自截止日期。
- 完成任务从 today 视图隐藏，但在全部视图可见。
- 下一步要做一个小原型来确认交互。

这时可以调用：

```text
/handoff

请把当前 Todo MVP 的目标、已决策事项、明确排除项、下一步建议整理成 handoff。
要求下一位 agent 能直接接着做 prototype，不需要重问背景。
```

输出通常应该包含：

- 背景：为什么要做这个个人 Todo MVP。
- 当前决策：范围、数据、视图、交互原则。
- 排除项：登录、同步、标签、截止日期、提醒。
- 未解决问题：today 与全部视图的切换方式。
- 下一步：做一个低成本 prototype 或合成 spec。

`/handoff` 不是总结作文。它的目标是保存可执行上下文，让下一次会话少重复解释、少重新猜测。

<a id="teach"></a>
## 用 `/teach` 学会工作流

如果你的目标不只是做完 Todo MVP，而是学会这一套 Skills 工作方式，可以用 `/teach`。它适合把当前目录当成一个持续学习空间：今天学 `/grill-me`，明天学 `/to-spec`，后天复盘 `/implement` 为什么要带测试。

可以这样开始：

```text
/teach

我想学会 Matt Pocock Skills 的基本工作流。
请用个人 Todo MVP 带我练习：先教我什么时候用 /grill-me，
再让我自己写一段调用文本，你来点评。
```

一个短片段可能是：

```text
Codex: 先写一句你会给 /grill-me 的请求。不要写功能清单，写你的不确定性。
你: 我想做 Todo App，但不知道第一版要不要登录和标签。请先问我问题。

Codex: 这句可以用。再加强一点：告诉 agent 不要实现，只做澄清，并让它最后输出已决策/未决策列表。
```

`/teach` 和普通解释的区别在于它会保留学习状态：你学到哪一步、练过什么、下一次该复习什么。对于新手来说，这比一次性读完所有 Skill 名字更有效。

## 一个可以照抄的入门路径

如果你现在就想开始，不要把所有 Skills 一次用完。照这个最小路径走：

```text
/grill-me

我想做一个个人 Todo MVP。目标是每天打开就知道今天要做什么。
我还不确定要不要登录、后端、截止日期、标签和提醒。
请先连续追问我，直到第一版范围足够清楚。
最后请输出：已确定范围、明确不做的范围、剩余问题、建议下一步。
```

如果你不知道下一步：

```text
/ask-matt

这是 /grill-me 后得到的 Todo MVP 决策摘要：
...
我现在不知道应该 prototype、写 spec，还是直接实现。请帮我选流程。
```

如果你要暂停：

```text
/handoff

请把当前 Todo MVP 的上下文整理成 handoff。
下一位 agent 应该能从这里继续，不需要重新问我已经回答过的问题。
```

如果你想把这件事变成学习：

```text
/teach

请用这个 Todo MVP 教我 Codex Skills 的入门工作流。
每次只教一个 Skill，并让我写一段可模仿的调用文本。
```

这就是第一篇要建立的基础：Codex Skills 的核心不是“让 AI 更听话的一句话”，而是把你和 agent 的协作方式变得稳定、可复用、可交接。等这个心智模型站稳，第二篇再进入真实仓库里的主链路：setup、带文档的 grilling、spec、tickets、implement、TDD 和 code review。
