# 03 - 第一次进入项目：让 Codex 安全地开始工作

这一篇从“已经能运行 `codex` 并完成登录”之后开始。目标不是记很多命令，而是建立一个稳定工作节奏：先读项目、再计划、再修改、再验证。

<a id="open-project"></a>
## 进入项目根目录

每次使用前，先进入项目根目录：

```powershell
cd D:\你的项目目录
codex
```

不要在桌面、下载目录或用户目录里随便启动 Codex，然后让它猜项目在哪里。Codex 会根据当前目录读取文件、查看 Git 状态、加载 `AGENTS.md`，并决定哪些文件属于当前工作区。

如果你只想从别的目录启动，也可以用命令参数指定目录：

```powershell
codex --cd D:\你的项目目录
```

## 第一次提问应该问什么

刚进入一个项目时，先让 Codex 建立上下文：

```text
请先阅读这个项目的 README、配置文件和主要目录结构。然后用简短列表告诉我：这个项目是做什么的、如何启动、如何测试、最重要的目录有哪些。不要修改文件。
```

如果你已经有明确需求，可以先让它只分析和出计划：

```text
我想实现这个需求：...
请先分析相关文件并给出计划，不要修改文件。计划里写清楚要改哪些文件、为什么改、风险是什么、如何验证。
```

确认计划后再让它执行：

```text
按刚才的计划执行。完成后运行项目已有的测试或最小验证，并总结改了什么。
```

<a id="agents-md"></a>
## 用 AGENTS.md 写项目说明

`AGENTS.md` 可以理解为给 Codex 看的项目 README。Codex 开始工作前会读取相关的 `AGENTS.md`，把里面的规则作为项目上下文。

新项目可以先让 Codex 生成草稿：

```text
/init
```

然后人工检查并保留真正有用的内容。一个好的 `AGENTS.md` 通常包含：

- 项目结构和重要目录。
- 启动、测试、构建、格式化命令。
- 代码风格和命名习惯。
- 哪些文件不要随便改。
- 修改完成后的验证标准。
- 团队 review 或提交要求。

不要把 `AGENTS.md` 写成口号合集。短、准、能执行，比长篇抽象规则更有用。

<a id="permissions"></a>
## 审批与沙箱

Codex 有两层安全控制：

| 控制 | 作用 |
| --- | --- |
| 沙箱 | 限制 Codex 技术上能读写哪里、能不能访问网络 |
| 审批 | 决定 Codex 什么时候必须停下来问你 |

新手建议保持默认权限。默认工作方式通常允许 Codex 在当前工作区内读文件、改文件、运行必要命令；当它要访问网络、写到工作区外、执行高风险操作时，会请求批准。

如果你只想聊天、分析或审查，不想让 Codex 修改文件，可以在会话里切到只读权限：

```text
/permissions
```

选择只读或更保守的模式。

不要一开始就使用绕过审批和沙箱的高风险模式。只有在隔离的临时环境、一次性容器或团队明确批准的自动化环境中，才考虑放宽权限。

## 常用命令

| 命令 | 用途 |
| --- | --- |
| `codex` | 启动交互式 Codex CLI |
| `codex --version` | 查看版本 |
| `codex login` | 登录 |
| `codex login status` | 检查认证状态 |
| `codex logout` | 登出 |
| `codex --cd <路径>` | 指定工作目录 |
| `codex --model <模型>` | 本次运行指定模型 |
| `codex --ask-for-approval <模式>` | 本次运行指定审批模式 |

进入交互式会话后，可以用：

```text
/help
```

查看当前版本支持的斜杠命令。具体命令会随版本变化，遇到差异时以 `/help` 和官方命令参考为准。

## 推荐工作方式

对新手来说，最稳的节奏是：

```text
先让 Codex 读项目
  -> 再让 Codex 给计划
  -> 你确认计划
  -> 再允许它修改文件
  -> 修改后运行验证
  -> 最后让它总结改动和风险
```

如果任务很小，可以直接让 Codex改，但仍建议要求它最后验证：

```text
请修复这个拼写问题。改完后运行最小相关检查，并告诉我改了哪个文件。
```

如果任务较复杂，先让它拆分：

```text
这个需求可能涉及多个模块。请先拆成 3 到 5 个可独立验证的小步骤，不要改文件。
```

## 什么时候使用桌面端

CLI 适合终端优先的开发流程。ChatGPT 桌面端更适合：

- 同时管理多个项目或长任务。
- 查看文件改动和结果。
- 使用内置浏览器验证本地页面。
- 配合插件、技能、计划或可视化能力。
- 在 Windows 上使用原生 PowerShell agent 或切换到 WSL agent。

如果你不知道选哪个，可以从 CLI 开始；需要更强的项目管理和可视化检查时，再使用桌面端。

## 常见问题

### Codex 没读到我的项目规则

确认 `AGENTS.md` 在项目根目录或当前目录向上的路径中。Codex 通常在会话启动时读取这些规则；如果你刚新增或修改了 `AGENTS.md`，重新启动会话更稳。

### Codex 请求网络访问

默认本地沙箱通常关闭网络访问。如果 Codex 要安装依赖、访问外部 API、拉取文档或下载资源，它可能会请求批准。批准前先看清楚它要访问什么、为什么需要访问。

### Codex 想修改工作区外的文件

先停下来确认原因。常见情况包括全局配置、缓存目录、系统路径或错误的当前目录。新手不要随便批准写入工作区外的操作。

### Windows 里 PowerShell 脚本被阻止

如果项目命令或 npm 脚本报执行策略错误，可以先换 CMD 或 Git Bash。确实需要 PowerShell 脚本时，再了解并调整执行策略，不要为了省事直接放开所有限制。

## 本篇总校验

你已经可以日常使用 Codex，如果：

- 能在项目根目录启动 `codex`。
- 知道第一次先让 Codex 读项目，而不是直接大改。
- 知道用 `AGENTS.md` 保存项目级规则。
- 知道审批和沙箱分别控制什么。
- 知道修改后要让 Codex 运行测试或最小验证。
- 知道遇到权限请求时先判断风险，再批准。
