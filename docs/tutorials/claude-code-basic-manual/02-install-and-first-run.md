## 从哪个入口开始

Claude Code 可以出现在不同入口里：CLI、IDE、桌面端和 Web。它们不是谁完全替代谁，而是适合不同工作姿势。

| 入口 | 适合场景 | 使用时要记住 |
| --- | --- | --- |
| CLI | 进入真实仓库、跑命令、改文件、验证结果，是最适合学习完整工作流的入口。 | 启动目录就是项目现场；先确认自己在哪个目录。 |
| IDE | 边看代码边协作，适合围绕当前文件、局部模块、编辑体验做任务。 | 不要只依赖当前打开文件；需要时仍要让 Claude 阅读相关上下文。 |
| 桌面端 | 适合在图形界面里管理任务、查看会话、处理较长工作流。 | 仍要关注连接到的目录、工具和权限范围。 |
| Web | 适合提问、讨论方案、做轻量分析或跨设备延续思考。 | 通常不等同于直接在本地仓库里执行修改和验证。 |

新手如果想系统建立 Claude Code 工作流，建议先从 CLI 开始。原因不是 CLI 更“高级”，而是它最直接暴露了真实开发闭环：你在哪个目录启动、Claude 读了哪些文件、要不要允许命令、改完是否运行测试，这些边界都比较清楚。

IDE、桌面端和 Web 后面都可以用，但第一次学习时先把“当前工作目录、文件读写、命令执行、验证结果”这条线走通，会更稳。

## 第一次启动前先确认目录

Claude Code 的很多判断都从当前工作目录开始。你在项目根目录启动，它看到的是一个项目；你在下载目录、桌面或用户目录启动，它看到的可能是一堆无关文件。

推荐做法是先进入项目根目录，再启动：

```powershell
cd D:\你的项目目录
claude
```

项目根目录通常能看到 README、Git 配置、依赖配置、源码目录和测试目录。例如：

```text
README.md
package.json
src/
tests/
.git/
```

第一次进入仓库后，可以先让 Claude 做只读理解：

```text
请先阅读当前项目的 README、主要配置文件和目录结构，然后告诉我：
1. 这个项目是做什么的
2. 如何启动
3. 如何运行测试
4. 最重要的目录有哪些

不要修改文件。
```

这个提示的关键不是模板本身，而是三个边界：先读项目、输出可继续使用的摘要、明确不要修改文件。

## 工作目录和读写范围

你可以把工作目录理解成 Claude Code 进入项目现场时站的位置。它会围绕这个位置搜索文件、读取上下文、运行命令，也可能在你允许后修改文件。

第一次使用时，先记住几个原则：

- 在正确项目根目录启动，而不是让 Claude 猜项目在哪里。
- 让 Claude 先说明它准备读取哪些文件，尤其是陌生仓库或大仓库。
- 修改前要求它说清楚要改哪些文件、为什么改、如何验证。
- 不要把含有密钥、客户数据、个人隐私或未获授权源码的目录随意交给 Claude。
- 如果工具提示要访问当前项目之外的目录，先停下来确认原因。

`CLAUDE.md`、项目规则和后续章节里的上下文管理都建立在这个基础上：Claude 需要足够上下文才能做事，但上下文必须和任务有关，读写范围也必须可解释。

## 工具调用不是魔法

Claude Code 通过工具完成任务。常见动作包括读取文件、搜索文本、编辑文件、运行命令、查看 Git 状态，或通过外部连接读取 issue、PR、文档和设计稿。

第一次看到工具调用提示时，不要只把它当成烦人的确认框。它其实在告诉你三件事：

1. Claude 准备做什么。
2. 这个动作会影响哪些文件、命令或外部系统。
3. 你是否愿意在当前范围内授权它继续。

读文件和搜索通常风险较低，但仍要注意敏感目录。编辑文件会改变工作区，需要你后续看 diff。运行命令的风险差异更大：`npm test`、`pytest`、`git status` 通常是开发验证动作；删除文件、批量替换、数据库迁移、部署发布则需要更谨慎的人工确认。

一个稳妥的第一次协作节奏是：

```text
只读了解
  -> 让 Claude 说明计划
  -> 你确认范围
  -> 允许小步修改
  -> 运行最小验证
  -> 查看 diff 和总结
```

这比“一开始就给所有权限，让它自己发挥”更适合真实项目。

## 如何看待首次授权提示

首次授权提示的目标不是阻止你使用 Claude Code，而是帮你建立边界。你不需要害怕每一次提示，也不应该默认全部放行。

可以用这几个问题判断：

| 看到提示时问自己 | 如果答案不清楚 |
| --- | --- |
| 这个动作和我当前任务有关吗？ | 让 Claude 解释为什么需要这个动作。 |
| 它会读写哪些目录或文件？ | 要求先列出范围，再决定是否继续。 |
| 它会运行什么命令？ | 先确认命令是不是只读、测试、构建或会产生副作用。 |
| 是否涉及密钥、数据、部署、删除或批量修改？ | 暂停，要求计划、备份或人工确认。 |

特别要避免把绕过权限当作日常习惯。更健康的最小权限心智模型是：先给完成当前步骤所需的最小能力；当任务推进到新步骤，再授权新的动作。

`CLAUDE.md` 可以提醒 Claude 遵守团队约定，但它不是强制安全边界。真正需要强制阻止的操作，应在后续通过 permissions、hooks、组织策略或受控环境处理。本章先记住这一层差异即可。

## 第一次让 Claude 读取哪些上下文

进入一个真实仓库时，不要让 Claude 一口气读取全仓。更好的做法是先读稳定入口，再按问题收窄。

第一次只读了解时，可以让它优先看：

- `README.md`、`CONTRIBUTING.md` 或项目说明。
- 包管理和构建配置，例如 `package.json`、`pyproject.toml`、`pom.xml`、`go.mod`。
- 项目规则文件，例如 `CLAUDE.md`、`AGENTS.md`、`.claude/` 下的说明，前提是仓库确实有这些文件。
- 主要源码目录和测试目录的结构。
- 当前任务相关的 issue、spec、ticket 或设计说明。

可以这样说：

```text
请先只读了解这个仓库。优先阅读 README、项目配置、项目规则文件和主要目录结构。不要读取无关的大型生成文件，不要修改文件。最后请列出你读过的文件、项目启动/测试方式，以及你还不确定的问题。
```

这个输出会成为第 03 章的起点：让 Claude Code 先读懂真实项目，而不是一进仓库就改代码。

## 最小权限心智模型

第一次使用 Claude Code，先用这套简单规则：

1. 先站对地方：在项目根目录启动。
2. 先只读：让 Claude 阅读 README、配置、规则和目录结构。
3. 先收束：让 Claude 说明相关文件、计划和验证方式。
4. 再授权：只允许当前步骤需要的读、写或命令。
5. 再验证：修改后看 diff，运行最小相关测试或检查。
6. 有风险就停：删除、迁移、发布、密钥、外部系统写入都需要额外确认。

这不是为了把使用过程变慢，而是为了让 Claude Code 的能力进入可控轨道。真正熟练之后，你会更快判断哪些提示可以放行，哪些动作需要先问清楚。

## 本章校验

读完本章，你应该能确认：

- 如果还没安装好 Claude Code，应去读已有的 [CLI 安装与使用教程](../claude-code-cli/README.md)，而不是在本章找重复安装正文。
- CLI、IDE、桌面端和 Web 是不同入口：CLI 最适合学习完整项目工作流，IDE 适合贴近编辑器的协作，桌面端适合图形化会话管理，Web 适合轻量讨论和跨设备思考。
- 工作目录会影响 Claude Code 能读什么、改什么、运行什么命令。
- 首次授权提示应按任务相关性、读写范围、命令副作用和敏感数据风险来判断。
- `CLAUDE.md` 是行为引导，不是强制安全机制；强制边界要靠 permissions、hooks、组织策略或受控环境。
- 第一次进入仓库时，应先让 Claude 读取 README、配置、项目规则和目录结构，并明确不要修改文件。
