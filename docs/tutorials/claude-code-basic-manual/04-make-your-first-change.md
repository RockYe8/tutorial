# 04 - 完成第一次小范围修改

上一章把真实项目读到一个可以执行的状态：相关文件、最小修改范围、风险和验证命令都已经收束出来。

这一章进入第一次改代码。目标不是让 Claude Code 展示“它能改很多”，而是学会让它完成一个足够小、能 review、能验证、能提交前总结的闭环。

一个好的第一次修改应该像这样：

```text
需求说清楚
  -> 判断直接执行还是先计划
  -> 说明会改哪些文件以及为什么
  -> 修改最小相关文件
  -> 查看 diff 并收束偏差
  -> 运行最小相关验证
  -> 提交前总结
```

这个闭环比“让 Claude 写完代码”更重要。你真正要建立的是可控交付习惯：知道改了什么，为什么改，怎么确认它没跑偏。

## 先把需求缩到可以执行

不要一上来把需求写成模糊愿望：

```text
帮我优化登录。
```

这句话太大。Claude 可能从文案、样式、性能、认证流程、错误处理一路展开，最后 diff 比你的真实需求大得多。

更适合第一次修改的是一个具体、可验证的小任务：

```text
请修改登录失败时的错误提示文案。

目标：
- 当密码错误时，把提示从 "Invalid credentials" 改成 "邮箱或密码不正确"。
- 不改变认证逻辑、接口返回结构或登录流程。
- 如果项目已有对应测试，只更新最小相关测试。

请先说明你准备修改哪些文件以及原因，再开始编辑。
```

这段话做了四件事：

- 说明目标结果，而不只是说“优化”。
- 明确不改什么，提前挡住范围扩散。
- 把测试限定在“已有对应测试”或“最小相关测试”。
- 要求 Claude 在编辑前说明文件范围。

第一次改代码时，需求越小越好。小不是价值低，而是反馈快。你可以更容易看懂 diff，也更容易判断 Claude 有没有理解项目约束。

## 什么时候可以直接执行

不是所有任务都需要先进入 planning mode。把 planning 写成每个小任务的仪式，会让简单工作变慢，也会让读者误以为“开始前必须先写计划”。

适合直接执行的任务通常满足这些条件：

- 影响范围清楚，通常只涉及一个文件或少数几个文件。
- 需求能用一句具体结果描述。
- 不改变公共接口、数据结构、权限、安全、账单或迁移逻辑。
- 有现成测试、快照、lint 或手工检查方式可以验证。
- 即使做错，也容易通过 diff 看出来并回退。

例如：

```text
请把设置页中“保存成功”的 toast 文案改成“设置已保存”。
只修改文案，不调整 toast 触发逻辑或样式。
修改后请展示 diff，并说明是否需要运行测试。
```

这种任务不必先写厚计划。你可以让 Claude 先定位文件、说明改动点，然后直接改。关键是“直接执行”不等于“随便执行”：它仍然要说明范围、展示 diff，并完成最小验证。

## 什么时候先调查和计划

中等任务不一定大，但通常有不确定性。比如你知道要改一个行为，却不知道入口在哪里、会影响哪些测试，或者有两三种实现方式。

这类任务适合先调查、列计划，再修改：

```text
我想让用户资料页支持显示昵称为空时的 fallback 文案。

请先只读调查：
1. 用户资料页的数据从哪里来
2. 昵称字段在哪里渲染
3. 现有测试覆盖了哪些路径
4. 你建议修改哪些文件以及为什么
5. 最小验证命令是什么

先不要编辑文件。给出计划后等我确认。
```

计划不需要长，但应该回答能不能安全执行：

```text
计划请包含：
- 目标行为
- 需要修改的文件
- 每个文件的改动原因
- 不会修改的范围
- 风险和不确定点
- 最小验证方式
```

一个合格计划可能长这样：

```text
我建议只修改两个文件：

1. src/pages/Profile.tsx
   这里渲染昵称。会在 displayName 为空时显示 "未设置昵称"。

2. src/pages/Profile.test.tsx
   已有资料页渲染测试。会补一个 displayName 为空的用例。

不修改：
- API 响应结构
- 用户资料保存逻辑
- 全局用户模型

最小验证：
- npm test -- Profile.test.tsx
```

这个计划的价值不是形式，而是让你能在动手前审查范围。如果你发现它准备改全局用户模型，就可以马上收束：

```text
不要修改全局用户模型。请重新给出只在资料页展示层处理 fallback 的计划。
```

## 让 Claude 说明会改哪些文件

开始编辑前，让 Claude 说明“哪些文件、为什么”。这一步很小，但能提前发现很多偏差。

可以用这个格式：

```text
在编辑前，请先列出：

- 你准备修改的文件
- 每个文件的修改目的
- 你确认不需要修改的相关文件
- 修改后要运行的最小验证命令

如果你发现需要扩大范围，请先停下来说明原因。
```

这里的重点是“相关但不修改”的文件。Claude 读到一个文件，不代表它应该改那个文件。比如它可能读过路由、数据模型和测试，但最终只需要改展示组件和对应测试。

当 Claude 说“顺便整理一下命名”“顺便抽一个 helper”“顺便更新样式”时，你要判断这是不是当前验收标准的一部分。如果不是，就先收回：

```text
这次先不要整理命名或抽 helper。
只完成错误提示文案修改和必要测试更新。
把其他想法记录为后续建议。
```

## 执行修改时保持小步

确认范围后，可以让 Claude 编辑：

```text
按刚才确认的计划执行。

要求：
- 只修改计划中列出的文件。
- 如果必须修改计划外文件，先停下来说明原因。
- 修改完成后展示 diff 摘要，不要直接提交。
```

第一次修改时，不建议把多个目标塞在一起：

```text
修改登录错误提示，顺便清理登录页样式，再补测试，再重构 auth service。
```

这会让 review 变得困难。即使每个点本身都合理，放在同一个 diff 里也会混淆问题：如果测试失败，你很难知道是文案、样式、测试还是重构导致的。

更稳的做法是把它拆成连续的小闭环：

```text
第一步：只改错误提示文案并验证。
第二步：如果需要，再单独开任务整理样式。
第三步：重构 auth service 作为独立任务，先计划再执行。
```

小步不是保守，而是让每一步都能被理解、审查和验证。

## 用 diff review 检查有没有跑偏

改完后，不要只问“完成了吗”。你应该让 Claude 做 diff review：

```text
请 review 当前 diff：

1. 按文件说明改了什么
2. 哪些改动直接对应我的需求
3. 有没有超出需求的改动
4. 有没有只读调查时发现但这次没有处理的问题
5. 接下来应该运行的最小验证命令
```

diff review 要看的不是代码是否“看起来不错”，而是范围是否正确：

- 是否只改了计划中的文件。
- 是否出现无关格式化、重命名、重排 import 或风格清理。
- 是否把小需求扩展成架构调整。
- 是否更新了必要测试，但没有补一堆无关测试。
- 是否有生成文件、锁文件或大型产物被意外改动。

如果发现偏差，不要继续往前冲。先收束 diff：

```text
diff 里包含了无关格式化。请只保留和本需求相关的改动。
不要改变业务逻辑，也不要修改没有必要的测试快照。
```

如果偏差来自真实问题，例如 Claude 发现现有代码里有一个相邻 bug，也不要顺手修：

```text
这个问题看起来真实存在，但不属于本次需求。
请把它记录为后续 ticket 建议，本次只完成当前验收标准。
```

这就是 scope creep 的边界：不是看它是否“有用”，而是看它是否属于当前任务。

## 运行最小相关验证

每次修改都要有验证，但验证不一定从全量测试开始。第一次小改动的默认顺序是先最小相关验证，再根据风险扩大。

常见层级是：

| 修改类型 | 最小验证 |
| --- | --- |
| 文案或 Markdown | 检查目标文件存在、链接可达、标题和内容范围正确。 |
| 单组件展示逻辑 | 运行对应组件测试，必要时手工检查页面。 |
| 单函数行为 | 运行对应单元测试。 |
| API 行为 | 运行相关 API 测试或集成测试。 |
| 类型或接口变更 | 运行相关测试，再运行 typecheck。 |
| 跨模块改动 | 运行相关测试、lint/typecheck，必要时扩大到全量测试。 |

你可以这样要求：

```text
请运行最小相关验证。

如果验证失败：
1. 先解释失败是否和本次改动有关
2. 如果相关，修复后重新运行同一验证
3. 如果无关，只记录为已有问题，不要扩大修改范围

最后总结运行了什么、结果如何、还有什么没有验证。
```

验证失败时，最重要的是先分类。不要看到失败就让 Claude 开始大修。很多项目里本来就有不稳定测试、环境缺失或历史失败；这些都不应该自动变成当前 ticket 的工作范围。

## 提交前总结

在提交或交给人 review 前，让 Claude 输出一个短总结：

```text
请给出提交前总结：

- 修改了哪些文件
- 每个文件为什么需要改
- 满足了哪些验收标准
- 运行了哪些验证，结果是什么
- 没有验证什么，以及原因
- 是否发现需要后续 ticket 处理的问题
```

这个总结可以直接转成 commit message、PR 描述或 handoff。它也能帮助你发现遗漏：如果 Claude 说不清验证结果，说明还没到“完成”的状态。

一个好的总结应该具体：

```text
修改文件：
- src/pages/Profile.tsx：在 displayName 为空时显示 "未设置昵称"。
- src/pages/Profile.test.tsx：增加昵称为空时的渲染用例。

验证：
- npm test -- Profile.test.tsx：通过。

未处理：
- 资料编辑页也有类似 fallback 需求，但不属于本次任务，建议另开 ticket。
```

注意这里没有写“已全面验证系统”。除非真的跑过全量测试、手工流程和相关集成验证，否则不要让总结说得比证据更大。

## 一个完整的小范围修改会话骨架

下面是可以模仿的完整节奏：

```text
第一轮：收束需求
请把登录失败时的错误提示从 "Invalid credentials" 改成 "邮箱或密码不正确"。
不改变认证逻辑、接口结构、样式或路由。
请先说明你准备修改哪些文件、为什么，以及最小验证方式。

第二轮：确认或收窄计划
只修改登录页展示和对应测试。
不要重构 auth service，也不要整理无关 import。
按这个范围执行。

第三轮：执行后 diff review
请 review 当前 diff：
1. 按文件说明改了什么
2. 哪些改动对应需求
3. 有没有超出需求的改动
4. 应运行什么最小验证

第四轮：验证和修复
请运行最小相关测试。
如果失败，先判断失败是否由本次改动引起；只修复当前需求相关失败。

第五轮：提交前总结
请总结修改文件、验收标准、验证结果、未验证内容和后续 ticket 建议。
```

这套骨架不是固定咒语。你要学的是其中的节奏：先收束，后执行；先看 diff，后宣布完成；先最小验证，后决定是否扩大。

## 应避免的误区

- 把“优化”“调整”“完善”这类模糊词直接交给 Claude 执行。
- 小任务也要求长 planning，让计划变成拖慢反馈的仪式。
- 中等任务不调查、不列文件范围，直接让 Claude 猜入口。
- 改完不看 diff，只听 Claude 说完成。
- 看到相邻问题就顺手修，导致当前 diff 失去单一目标。
- 验证失败后不分类，直接扩大修改范围。
- 提交前总结只写“已完成”，没有文件、验证和残余风险。

## 本章校验

读完本章，你应该能做到：

- 把第一次修改缩到一个具体、可验证的小范围需求。
- 区分适合直接执行的小任务，以及应该先调查、列计划再修改的中等任务。
- 要求 Claude 在编辑前说明会修改哪些文件、为什么，以及不会修改什么。
- 在修改后用 diff review 检查范围、无关改动和潜在偏差。
- 运行最小相关验证，并在失败时先判断是否属于当前改动。
- 用提交前总结说明修改文件、验收标准、验证结果、未验证内容和后续建议。

下一章会继续强化验证闭环：当任务从“小改动”进入 bug、测试失败或复杂验证时，如何先复现、再定位、再修复，而不是让 Claude 靠猜。
