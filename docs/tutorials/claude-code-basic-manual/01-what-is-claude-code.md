# 01 - 什么是 Claude Code

[返回目录](README.md) | [下一章：安装与第一次启动](02-install-and-first-run.md)

这一章先回答一个最基础、也最容易被误解的问题：Claude Code 到底是什么？

你可以把 Claude Code 理解成一个进入项目现场工作的 agentic coding tool。它不是只在聊天框里回答问题，也不是只在编辑器里补全下一行代码；它可以在你授权的工作目录里读取仓库、搜索文件、编辑文件、运行命令，并连接开发工具。研究底稿引用的 Claude Code Overview 也把它的核心能力概括为：读取代码库、编辑文件、运行命令、集成开发工具。

这句话的重点不是“Claude 更会写代码”，而是“Claude Code 能围绕一个真实项目做事”。真实项目里，任务通常不会只发生在一个 prompt 里：你要先理解目录结构，找到相关文件，确认约束，修改代码，运行测试，看 diff，再决定是否提交或创建 PR。Claude Code 的价值就在这个闭环里。

## 它不是普通聊天

普通聊天适合解释概念、讨论方案、改写片段。你把代码粘进去，它可以分析；你给一段报错，它可以推测原因。但聊天本身通常不在你的仓库现场。

Claude Code 的工作方式更接近：

```text
进入当前项目
  -> 读取 README、配置、源码和测试
  -> 找到和任务相关的文件
  -> 提出修改计划或直接做小改动
  -> 编辑文件
  -> 运行测试、lint、typecheck 或项目脚本
  -> 总结 diff、验证结果和未完成风险
```

也就是说，它不只是“回答你应该怎么改”，而是可以在你允许的范围内实际改文件、跑命令、回收反馈。

这会改变你提问的方式。与其问：

```text
这个项目怎么实现登录？
```

更适合问：

```text
请先阅读 README、路由、认证相关代码和测试，告诉我这个项目的登录流程经过哪些模块。不要修改文件。
```

前者像是在问一个通用助手，后者是在让 Claude Code 进入项目上下文，产出可以继续开发的理解。

## 它也不是 IDE 补全

IDE 补全通常围绕你正在编辑的文件或光标位置工作。它擅长补全函数、生成样板代码、猜下一段实现。它很快，也很贴近编辑动作。

Claude Code 的边界更大。它可以跨文件理解一个任务：先看调用方，再看实现，再看测试，再看配置；它也可以在修改后运行验证命令，用失败结果继续定位问题。

举个小例子：如果你要改一个参数名，IDE 补全可能帮你改当前函数附近的代码；Claude Code 更适合帮你先找这个参数在路由、类型定义、测试和文档里的使用位置，然后小步修改并运行相关测试。

所以不要把 Claude Code 当成“更大的自动补全”。更好的心智模型是：它是一个会使用开发工具的协作者，但仍需要你给清楚任务、边界和验收方式。

## 它适合做什么

研究底稿根据官方 overview 和 common workflows 总结了 Claude Code 的典型任务：理解陌生代码库、实现功能、修复 bug、写测试、重构、生成文档、创建提交和 PR，以及自动化重复性开发任务。

放到日常开发里，可以这样理解：

| 任务 | 适合交给 Claude Code 的部分 |
| --- | --- |
| 读陌生代码 | 让它先看 README、目录结构、关键模块和测试，输出架构概览、术语表或流程追踪。 |
| 实现小功能 | 给出目标、范围和验收标准，让它定位文件、修改代码，并运行最小相关验证。 |
| 修 bug | 提供报错、堆栈、复现步骤和失败命令，让它先复现或解释失败路径，再修复。 |
| 写测试 | 让它参考项目已有测试风格，补充边界条件，并运行新测试修正失败。 |
| 重构 | 明确“保持行为不变”和验证方式，让它分小步改动并检查 diff。 |
| 写文档 | 让它基于真实代码和变更记录生成说明、README 片段、PR 描述或 release notes。 |
| 创建 PR | 让它整理改动摘要、验证证据、风险和 review 重点，再进入团队审查流程。 |

这些任务的共同点是：它们都有上下文、有文件、有反馈，也最好有验证命令。

## 它不适合替你判断一切

Claude Code 能做很多事，但这不等于它应该自己决定所有事。

不适合的期待包括：

- 只说“把这个项目优化一下”，就期待它自动完成一个模糊大项目。
- 把架构取舍、产品边界、风险接受标准全部交给它决定。
- 不给复现步骤、不跑测试，却希望它稳定修好 bug。
- 让它绕过权限提示、跳过 review，直接把结果当成可发布版本。
- 把它描述成万能自动程序员，然后在失败时才补充上下文和约束。

更健康的用法是：你负责目标、判断和验收边界；Claude Code 负责在这些边界内阅读、修改、验证和总结。它可以扩大你的执行力，但不应该替代你的工程判断。

## 最小工作心智模型

第一次使用时，先记住这五件事就够了：

1. Claude Code 在项目目录里工作。启动位置、可读文件和可写范围会影响它能做什么。
2. 它通过工具做事。读文件、搜索、编辑、运行命令、连接外部工具，都应有清楚权限边界。
3. 上下文不是越多越好。给它和当前任务相关的文件、错误、约束和验收标准，通常比把所有背景都塞进去更可靠。
4. 小任务可以直接做；不确定、高风险或跨模块任务应先规划。
5. 修改完成不等于交付完成。测试、lint、typecheck、diff review 和人工 review 构成验证闭环。

这也是后续章节会反复展开的真实开发任务生命周期：

```text
理解项目
  -> 管理上下文
  -> 澄清任务与规划
  -> 修改代码
  -> 验证结果
  -> 沉淀规则
  -> 扩展为团队工作流
```

学 Claude Code，不是背一组命令，而是学会让一个 agent 在真实仓库里按可控、可验证、可交接的方式工作。

## 本章校验

读完本章，你应该能说清：

- Claude Code 是能读取仓库、编辑文件、运行命令并连接开发工具的 agentic coding tool。
- 它和普通聊天的差异在于：它能进入项目现场并围绕文件和命令形成闭环。
- 它和 IDE 补全的差异在于：它更适合跨文件、跨工具、带验证反馈的开发任务。
- 它适合明确、有上下文、有反馈的任务，不适合替代工程判断或自动完成模糊大项目。
