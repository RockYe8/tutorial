# 05 - 调试、测试与验证闭环

[上一章：完成第一次小范围修改](04-make-your-first-change.md) | [返回目录](README.md) | [下一章：上下文、memory 与 CLAUDE.md](06-context-memory-and-claude-md.md)

上一章完成了第一次小范围修改：先收束需求，再看 diff，最后运行最小相关验证。

这一章把验证闭环往前推一步。遇到 bug、测试失败或行为异常时，不要让 Claude Code 直接猜原因、改代码、再“跑一下看看”。更稳的做法是先建立可观察的失败，再定位、修复、验证，并把证据总结清楚。

## 本章底层逻辑：Red-Green-Refactor 的泛化

Red-Green-Refactor 不只适用于“先写一个失败单元测试，再修到通过”。在和 Claude Code 协作时，Red 更准确地说是：先建立一个可重复、可判断的失败反馈。它可以是一条失败测试，也可以是一条稳定报错的命令、一组清晰复现步骤、一次页面状态检查、日志里的关键错误，或一个最小验证命令。

只要这个反馈能在修复前稳定证明问题存在，并在修复后用同一标准判断是否变好，它就承担了 Red 的角色。后面的调试、测试和验证，本质上都是围绕这个反馈把问题从红推到绿，再收束改动范围。

一个健康的调试闭环应该像这样：

```text
描述症状和复现方式
  -> 收集错误信息、堆栈和失败命令
  -> 先建立红色反馈
  -> 定位原因并做最小修复
  -> 运行最小相关验证
  -> 按风险扩大到 lint / typecheck / review
  -> 总结验证证据和未覆盖范围
```

这里的核心不是“Claude 能不能很快写出修复”，而是它是否能证明修复真的解决了你交给它的问题。

## Debug 前先整理输入

调试任务最怕信息只有一句：

```text
登录坏了，帮我修。
```

这会把 Claude 推向猜测。它可能从路由、鉴权、表单、接口、缓存一路扫描，最后改动范围越来越大，却仍然没有证明自己修的是同一个问题。

更好的 debug 输入应包含这些信息：

| 信息 | 作用 |
| --- | --- |
| 现象 | 用户看到什么，或哪条测试、哪条命令失败。 |
| 期望结果 | 正常情况下应该发生什么。 |
| 实际结果 | 实际错误、错误码、页面状态或测试输出。 |
| 复现步骤 | 从干净状态开始，怎样稳定触发问题。 |
| 失败命令 | 具体运行了什么命令，例如 `npm test -- Login.test.tsx`。 |
| 错误信息和堆栈 | 尽量保留第一条关键错误和相关 stack trace，不要只贴最后一句。 |
| 最近变化 | 这个问题是否出现在某次改动、依赖升级或环境切换之后。 |
| 范围限制 | 哪些文件、行为或架构不希望这次顺手调整。 |

你可以这样交给 Claude：

```text
登录失败提示没有显示。

期望：
- 输入错误密码后，页面显示“邮箱或密码不正确”。

实际：
- 页面只停留在登录表单，没有错误提示。

复现步骤：
1. 启动本地应用
2. 打开 /login
3. 输入 test@example.com 和错误密码
4. 点击登录

失败命令：
- npm test -- Login.test.tsx

关键错误：
粘贴相关测试输出和 stack trace。

请先复现或用现有测试建立红色反馈。
先不要猜测修复，也不要重构认证流程。
```

如果日志很长，不必把几千行全部塞进对话。先给失败命令、第一条关键错误、相关堆栈、版本或环境差异，再让 Claude 说明它还需要哪一段日志。

## 先建立红色反馈

红色反馈指的是：在修复前，先有一个能稳定失败的测试、命令或复现步骤，用来证明当前问题真实存在。

这一步很重要。没有红色反馈，Claude 可能修到相邻问题，也可能把错误“绕过去”，最后你只得到一个看似合理的 diff。

可以这样要求：

```text
请先建立红色反馈：

1. 优先运行现有最小相关测试，确认失败。
2. 如果没有覆盖，请按项目既有测试风格补一个最小失败测试。
3. 测试只覆盖这个 bug，不要顺手扩大到无关边界条件。
4. 在看到失败前，不要开始修复实现。
```

这里的“红色”不一定永远是自动化测试。对文档、配置、构建或 UI 行为，红色反馈也可以是：

- 某个链接检查失败。
- 某条 lint 或 typecheck 报错。
- 某个最小构建命令失败。
- 一组清晰的手工复现步骤可以稳定看到错误。

但“我跑了一下页面，好像不对”还不够。它没有说明入口、步骤、实际结果和判断标准，也无法让下一轮验证复用。

## 让 Claude 生成测试时保持克制

测试生成不是越多越好。一个好的 bugfix 测试应当像探针：足够小，正好钉住当前失败。

你可以这样约束：

```text
如果需要新增测试，请遵守：

- 先阅读同目录已有测试风格。
- 只新增能复现当前 bug 的最小测试。
- 不重写测试框架、不批量整理旧测试。
- 不为了提高覆盖率顺手补一组无关场景。
- 新测试失败后，再开始修实现。
```

例如，当前问题是“昵称为空时资料页崩溃”，最小测试可能只需要覆盖一个空昵称输入。它不应该顺手覆盖头像、简介、权限、保存按钮和接口异常。那些也许有价值，但应进入后续 ticket，而不是混进当前修复。

测试失败后，也不要立刻让 Claude 大范围改。先让它分类：

```text
请解释这个失败：
- 是否由刚新增的测试暴露？
- 是否和当前 bug 直接相关？
- 如果相关，建议修改哪个最小实现点？
- 如果无关，请记录为已有问题，不要扩大本次修改范围。
```

这能避免“一个失败带出一串重构”的连锁反应。

## 定位和修复要围绕失败证据

有了红色反馈后，再让 Claude 定位原因。此时它应该把分析锚定在失败证据上，而不是泛泛扫描全项目。

一个合适的提示是：

```text
现在请基于这个失败定位原因。

要求：
- 说明失败路径经过了哪些文件或函数。
- 区分直接原因和可能的相邻问题。
- 给出最小修复方案。
- 修复前列出计划修改的文件。
- 如果需要扩大范围，先停下来说明原因。
```

修复方案应尽量小。调试时常见的范围漂移包括：

- 为了修一个空值错误，重构整个数据模型。
- 为了让测试通过，降低断言质量或删除失败测试。
- 为了处理一个特殊输入，改掉公共 API 契约。
- 为了消除类型错误，使用过宽的 `any` 或忽略错误。

如果 Claude 的计划看起来超出当前 bug，可以收束：

```text
这次只修复当前复现路径。
不要重构数据模型，也不要放宽测试断言。
请重新给出最小修复计划。
```

调试的目标不是让 diff 显得聪明，而是让失败证据从红变绿，并且不引入额外风险。

## 验证层级：从最小相关到更大范围

修复后，第一步是重新运行刚才失败的同一条验证。只有它通过，才能证明当前修复击中了目标。

常见验证层级可以这样理解：

| 层级 | 适合回答的问题 |
| --- | --- |
| 失败复现 / 单个测试 | 当前 bug 是否被修复。 |
| 相关测试文件或测试组 | 相邻行为是否仍然正常。 |
| lint | 代码风格、静态规则、明显坏味道是否被引入。 |
| typecheck | 类型契约、接口变化、跨文件调用是否仍一致。 |
| diff review | 改动范围是否符合任务，是否有无关编辑。 |
| 全量测试或构建 | 较大影响面下，系统整体是否仍能通过基础门槛。 |
| 人工 review / PR review | 设计取舍、可维护性、风险和业务语义是否合理。 |

不是每次都必须从第一层跑到最后一层。文案修复可能只需要文件检查、链接检查和 diff review；跨模块类型变更则通常需要相关测试、typecheck、lint，甚至全量测试。

你可以让 Claude 自己给出验证策略，但要要求它说明理由：

```text
请给出本次修复的验证层级：

- 必须运行的最小相关验证是什么？
- 根据改动范围，是否需要 lint 或 typecheck？
- 是否需要全量测试？如果不需要，请说明为什么。
- 哪些验证只能人工确认？
```

当验证失败时，不要直接扩大修改。先回到分类：

```text
验证失败后请先判断：

1. 失败是否由本次改动引起？
2. 失败是否属于当前 bug 的验收范围？
3. 如果属于，请修复并重新运行同一验证。
4. 如果不属于，请记录为后续问题，不要顺手处理。
```

验证闭环靠的是证据递进，而不是命令越多越安心。

## 用 diff review 收束范围

测试通过不代表任务就完成了。测试只能证明某些行为成立，不能证明 diff 没有跑偏。

修复后，让 Claude 做一次范围 review：

```text
请 review 当前 diff：

1. 哪些改动直接对应这个 bug？
2. 哪些测试证明了修复有效？
3. 有没有无关格式化、重命名、重构或依赖变化？
4. 有没有为了让测试通过而降低断言质量？
5. 是否有发现但未处理的相邻问题？
```

如果出现无关改动，先收束 diff，再继续验证。不要把无关清理和 bugfix 混在一起提交；否则后续 review 很难判断哪一行是真正的修复。

## Verification summary 模板

每次交付前，都应该让 Claude 给出验证总结。这个总结不是仪式，而是把“我认为完成了”变成“我有这些证据”。

可以使用这个模板：

```text
Verification summary

修改范围：
- 文件 A：做了什么，为什么需要。
- 文件 B：做了什么，为什么需要。

运行过的验证：
- 命令或检查 1：通过 / 失败；关键结果是什么。
- 命令或检查 2：通过 / 失败；关键结果是什么。

失败与修复：
- 如果有失败，说明失败原因、是否相关、如何修复、是否重跑通过。

未验证内容：
- 没有运行什么，原因是什么。
- 哪些行为需要人工确认。

后续问题：
- 发现但不属于本次范围的问题，建议新开 ticket。
```

一个更具体的例子：

```text
Verification summary

修改范围：
- src/pages/Login.tsx：在登录失败时渲染后端返回的错误文案。
- src/pages/Login.test.tsx：新增错误密码时显示错误提示的测试。

运行过的验证：
- npm test -- Login.test.tsx：通过，新增测试先失败，修复后通过。
- npm run typecheck：通过。

未验证内容：
- 没有运行全量 e2e；本次只修改登录页错误提示，影响范围集中在组件层。
- 没有手工检查真实后端错误码；当前测试使用项目已有 mock。

后续问题：
- 登录接口的错误码文案映射缺少统一表，不属于本次 bugfix，建议另开 ticket。
```

注意它没有写“系统已完全验证”。如果没有运行全量测试、没有做浏览器手工检查、没有覆盖真实后端，就应该明确说出来。诚实的未验证范围，比空泛的“全部正常”更有价值。

## 一个完整 debug 会话骨架

下面是一段可以模仿的节奏：

```text
第一轮：提供问题输入
我遇到登录失败提示不显示的问题。
这里是期望、实际结果、复现步骤、失败命令和关键堆栈。
请先建立红色反馈，不要直接修复。

第二轮：确认失败范围
请说明当前失败是否稳定复现。
如果需要新增测试，只新增覆盖这个 bug 的最小测试。

第三轮：定位并计划修复
基于失败证据定位原因。
修复前列出要修改的文件、最小改法和验证命令。

第四轮：执行最小修复
按确认的范围修复。
不要重构相邻代码，也不要降低测试断言。

第五轮：验证
先重新运行刚才失败的验证。
根据改动范围，再判断是否需要 lint、typecheck 或更大测试。

第六轮：diff review 和总结
请 review diff 是否只覆盖当前 bug。
最后输出 verification summary：运行了什么、结果如何、未验证什么、后续问题是什么。
```

这套骨架的重点不是固定话术，而是顺序：没有复现不猜修，没有红色不宣布绿色，没有验证证据不交付。

## 应避免的误区

- 只说“坏了”，不给复现步骤、失败命令、错误信息和期望结果。
- 没有建立红色反馈，就让 Claude 直接猜原因并修改。
- 把“跑一下看看”当作验证，却没有说明步骤、结果和判断标准。
- 为了让测试通过，删除失败测试、放宽断言或隐藏错误。
- 让 Claude 一次生成大量测试，把当前 bugfix 变成覆盖率工程。
- 验证失败后不分类，顺手修一堆历史问题。
- 测试通过后不看 diff，忽略无关重构、格式化或依赖变化。
- verification summary 只写“已验证”，没有命令、结果和未验证范围。

## 本章校验

读完本章，你应该能做到：

- 向 Claude 提供可用的 debug 输入：错误信息、堆栈、复现步骤和失败命令。
- 要求 Claude 先建立红色反馈，再定位和修复。
- 让 Claude 生成最小相关测试，而不是批量补测试。
- 按风险组合测试、lint、typecheck、diff review 和人工 review。
- 在验证失败时先分类，再决定是否修复或记录为后续问题。
- 用 verification summary 说明运行了什么、结果如何、未验证什么。
