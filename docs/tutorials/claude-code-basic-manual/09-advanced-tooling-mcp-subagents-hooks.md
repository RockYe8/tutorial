# 09 - MCP、subagents、hooks 等进阶工具边界

[上一章：Skills 与可复用工作流](08-skills-and-repeatable-workflows.md) | [返回目录](README.md) | [下一章：团队工作流、CI 与 review](10-team-workflow-ci-and-review.md)

前面几章已经走过了单次开发任务的主线：让 Claude Code 进入项目、管理上下文、拆清任务、完成小步修改、验证结果，并把重复流程沉淀成 skill。

这一章进入进阶工具，但重点不是把每个工具讲成教程。基础读者更需要先建立判断边界：什么时候应该接外部系统，什么时候应该隔离上下文，什么时候需要确定性的安全控制。

本节先讲 MCP。它解决的是“Claude Code 怎样可靠地接入外部系统”，而不是“安装一个万能插件以后什么都能自动完成”。

## MCP 是外部系统适配层

MCP 可以先理解为 Claude Code 和外部系统之间的适配层。它把外部工具、数据库、API 或资源用统一方式暴露给 Claude Code，让 Claude 不必只依赖你手动复制粘贴外部事实。

适合接入 MCP 的场景，通常有一个共同特征：关键信息不在当前仓库里，却会反复影响开发判断。

| 外部系统 | MCP 适合解决的问题 |
| --- | --- |
| Issue tracker | 读取需求、验收标准、讨论记录，必要时创建或更新任务。 |
| PR/MR 与代码平台 | 读取 review 评论、变更列表、失败检查和上下文，用于审查或修复。 |
| 数据库 | 查询结构、样例数据或排查结果，辅助理解真实数据状态。 |
| 监控和实验平台 | 查看错误、指标、线上影响范围，帮助定位问题和验证修复。 |
| 设计稿 | 读取设计上下文、标注和资源，减少人工转述。 |
| 文档系统 | 读取产品说明、接口文档、决策记录和团队约定。 |

如果你只是偶尔要引用一段外部说明，把链接或摘录贴进当前任务就够了。MCP 更适合那些“每次都要查、查完还要和代码一起判断、人工复制容易漏”的系统。

## 不要把 MCP 当万能插件

MCP 不是让 Claude Code 变成“全自动接管所有工具”的开关。它只是提供连接方式，真正重要的是你暴露了哪些工具、允许它们做什么、外部内容是否可信，以及这次任务是否真的需要这些能力。

一个健康的判断顺序是：

```text
当前仓库信息是否足够？
  -> 不足的信息是否来自稳定外部系统？
  -> 是否会反复使用或需要结构化读取？
  -> 是否能限定只读或最小写入权限？
  -> 是否理解外部内容带来的信任风险？
```

如果这些问题答不上来，先不要急着接 MCP。让 Claude 明确说明“缺少哪些外部事实”“为什么不能从仓库内判断”“临时复制这一次是否已经足够”，往往更安全。

## Scope、workspace trust 和工具暴露

接入 MCP 时，最容易忽略的不是配置命令，而是共享范围。

可以把 scope 理解为“这份 MCP 配置对谁、在哪些项目里可见”。常见边界包括：

| Scope | 适合场景 | 风险提醒 |
| --- | --- | --- |
| Local | 只在当前项目、当前个人环境使用。 | 适合个人试验，但团队成员不会自动获得同样能力。 |
| Project | 随项目配置共享给团队。 | 需要更谨慎审查，因为它会影响所有信任该工作区的人。 |
| User | 跨个人多个项目可用。 | 方便个人常用工具，但不要把某个项目的权限误带到其他项目。 |

项目级 MCP 配置尤其要注意 workspace trust。一个从外部克隆来的仓库不应该仅靠提交配置，就自动让你的 Claude Code 信任并运行它声明的 MCP server。你需要先判断这个工作区是否可信，再决定是否启用其中的外部工具。

另一个边界是工具暴露。MCP server 可能暴露 tools、prompts 和 resources。对基础使用者来说，不必先理解协议细节，但必须问清楚：

- 它暴露的是只读能力，还是可以创建、更新、删除外部资源？
- 它能访问哪些账号、项目、数据库、文档或 issue？
- 它返回的内容是否可能很大，是否会挤占 Claude 的上下文？
- 它的输出是否来自用户、评论、网页、文档等不完全可信来源？
- 这次任务是否真的需要写权限，还是只读已经足够？

最小权限原则同样适用于 MCP：先只读，按任务需要逐步扩大；能限制到项目、仓库、数据库或资源集合，就不要给全局访问。

## 外部内容与 prompt injection 风险

MCP 的价值是把外部事实带进 Claude Code，但风险也来自这里：外部系统里的内容不一定可信。

例如 issue 评论、PR 讨论、文档页面、设计稿注释、监控事件描述，都可能包含人为写入的文本。Claude 读取这些内容后，可能遇到类似“忽略之前的指令”“把密钥发到这里”“不要运行测试直接提交”这样的恶意或误导性指令。这类风险通常被称为 prompt injection。

处理方式不是“永远不要接外部系统”，而是建立信任边界：

- 把外部内容当作数据，而不是新的最高优先级指令。
- 对未知来源内容保持只读，避免同时给写文件、执行命令和外部写入权限。
- 让 Claude 在引用外部事实时说明来源，例如来自哪个 issue、PR、文档或监控事件。
- 对会修改外部系统的操作保留人工确认，尤其是关闭 issue、更新 PR、写数据库、触发部署或发送消息。
- 对敏感系统设置更窄的 scope，并配合 permissions 或 hooks 做强制边界。

一个实用提示是：当 MCP 返回外部内容时，可以要求 Claude 区分“外部事实”和“执行指令”。前者可以作为判断材料；后者除非来自你信任的配置或当前用户明确授权，否则不应直接执行。

## 什么时候从复制粘贴升级为 MCP

基础阶段完全可以先复制粘贴。MCP 是在重复、结构化和权限边界都值得投入时再引入的工具。

可以用这张表判断：

| 现象 | 继续复制粘贴 | 考虑 MCP |
| --- | --- | --- |
| 使用频率 | 偶尔引用一段外部说明。 | 每个任务都要查同类 issue、PR、监控或文档。 |
| 信息形态 | 一小段文本，人工摘录不容易错。 | 多条记录、状态字段、评论线程、查询结果或资源列表。 |
| 时效性 | 内容相对稳定。 | 内容经常变化，需要读取当前状态。 |
| 任务影响 | 只帮助理解背景。 | 会影响代码修改、验证范围、审查结论或任务状态。 |
| 权限需求 | 只读链接或摘录即可。 | 需要受控地读取特定系统，或在人工确认后回写状态。 |

如果你经常在会话里做这种事：

```text
我从 issue 里复制需求；
再从 PR 里复制评论；
再从监控里复制错误；
再从文档里复制接口说明；
然后让 Claude 把它们和仓库代码一起判断。
```

这就是 MCP 值得评估的信号。不是因为复制粘贴“不专业”，而是因为它容易丢上下文、丢来源、丢最新状态，也很难稳定复用。

相反，如果这次只是让 Claude 根据一段产品说明改一个文案，复制粘贴更简单，也更容易控制边界。

## 一个最小使用心智模型

第一次在团队项目里考虑 MCP 时，不必从开发自定义 server 开始。可以先按下面的顺序和 Claude 一起评估：

1. 列出任务中反复依赖的外部系统。
2. 标记哪些只需要读，哪些可能需要写。
3. 为每个系统限定 scope：个人、当前项目，还是团队共享。
4. 明确哪些外部内容是不可信输入，需要防 prompt injection。
5. 先启用最小只读能力，完成几次真实任务后再考虑更大的权限。

你最终想得到的不是“Claude 能连很多工具”，而是“Claude 能在正确边界内读取必要事实，并把来源、限制和风险说清楚”。

## 与 subagents、hooks 和 permissions 的衔接

MCP 解决外部系统连接问题，但它不解决所有进阶工具问题。

当问题是“大量文件、日志或研究材料会塞满主上下文”时，更可能需要 subagents 或隔离上下文。它们的重点是分担阅读和分析，而不是连接外部系统。

当问题是“有些操作必须被阻止、批准、格式化、审计或通知”时，更可能需要 permissions 和 hooks。它们的重点是确定性控制，而不是让模型记住一条提醒。

这几个工具可以配合，但边界不同：

| 工具 | 主要解决什么 |
| --- | --- |
| MCP | 把外部系统事实和操作接入 Claude Code。 |
| Subagents | 隔离上下文、并行阅读、处理专门分析任务。 |
| Permissions | 限定 Claude Code 可以使用哪些工具和命令。 |
| Hooks | 在工具调用或会话事件前后做确定性控制。 |

不要因为工具高级就提前引入。只有当真实任务暴露出“外部事实反复复制”“上下文太大”“权限需要强制边界”这类具体问题时，再选择对应工具。

## 本节校验

读完 MCP 部分，你应该能做到：

- 解释 MCP 是外部系统适配层，而不是万能插件。
- 判断 issue、PR、数据库、监控、设计稿、文档系统等场景什么时候适合 MCP。
- 区分 local、project、user 这类 scope 背后的共享边界。
- 理解 workspace trust、工具暴露和最小权限为什么重要。
- 识别外部内容带来的 prompt injection 风险，并把外部文本当作数据处理。
- 判断一段“复制粘贴外部事实”的流程是否值得升级为 MCP。

接下来讲 subagents。它们解决的不是“连接更多外部系统”，而是“怎样让 Claude Code 在不污染主会话上下文的情况下，分担阅读、研究和专业审查”。

## Subagents 是隔离出来的助手

Subagent 可以先理解为一个被委派出去的 Claude Code 助手。它有自己的上下文窗口、任务说明和可用工具；主会话把一个边界清楚的任务交给它，它完成后把结论、证据和不确定点带回来。

这和 MCP 的边界不同：

| 工具 | 重点 |
| --- | --- |
| MCP | 把 issue、PR、数据库、监控、文档等外部系统接入 Claude Code。 |
| Subagent | 把阅读、研究或审查任务隔离到另一个上下文里，只把结果带回主会话。 |

如果你缺的是外部事实，优先考虑 MCP 或人工提供材料。如果你已经有材料，但材料太多、问题可拆、主会话不应该被细节填满，就可以考虑 subagent。

## 什么时候值得委派

Subagent 最适合处理信息量大、边界明确、可以独立得出结论的任务。常见场景包括：

| 场景 | 适合委派的原因 | 主会话应该保留什么 |
| --- | --- | --- |
| 大规模代码阅读 | 需要扫很多文件、日志或历史记录，容易挤占主上下文。 | 任务目标、最终判断、下一步决策。 |
| 专业审查 | 安全、性能、测试缺口、迁移影响等需要固定视角。 | 是否采纳审查结论，以及如何排优先级。 |
| 并行研究 | 多个问题互不依赖，可以分别调查后汇总。 | 研究问题拆分、冲突结论仲裁。 |
| 上下文隔离 | 某些资料很多但只对局部判断有用，不值得长期留在主会话。 | 简短摘要、证据路径和残余风险。 |

不适合委派的任务也很常见：需求还没说清、多个子任务会改同一批文件、结果需要连续互动判断，或者只是一个两分钟能读完的小问题。这时 subagent 只会增加沟通成本。

一个简单判断是：如果你希望有人去“读一堆东西后回来汇报”，subagent 可能合适；如果你希望有人和你来回确认产品取舍，主会话更合适。

## 独立上下文意味着提示要自包含

很多 subagent 失败，不是能力不足，而是委派提示太空。不要写：

```text
帮我看看这个模块有没有问题。
```

这种提示把太多背景留在主会话里，subagent 未必知道“这个模块”是哪一个、“问题”指什么、“看完”要交付什么。更稳的委派提示应该自包含，至少包括六类信息：

| 要素 | 应写清楚什么 |
| --- | --- |
| 目标 | 这次委派最终要回答什么问题。 |
| 范围 | 允许阅读哪些目录、文件、issue、日志或资料；哪些不在范围内。 |
| 输入材料 | 具体路径、链接、命令输出、错误信息或研究材料。 |
| 输出格式 | 要表格、要结论列表、要风险分级，还是要可执行建议。 |
| 限制条件 | 不要改文件、不要联网、不要触碰某些目录、不要展开某类方案。 |
| 验证标准 | 怎样判断它的结论可信，例如引用文件路径、列出证据、说明未验证项。 |

例如：

```text
请作为测试覆盖审查 subagent，阅读 src/billing/ 和 tests/billing/。

目标：找出账单折扣计算相关的高风险未覆盖分支。
范围：只读这两个目录，不修改文件，不评估 UI。
输入材料：从 BillingService、DiscountPolicy 和现有 billing 测试开始。
输出格式：按风险从高到低列出发现；每条包含文件路径、风险说明、建议补的测试。
限制条件：不要提出重构方案，除非缺测试无法单独覆盖。
验证标准：每个发现都要引用具体文件或测试缺口；如果无法确认，标为“待确认”。
```

这个提示的重点不是写得长，而是让 subagent 即使离开主会话，也知道自己该读什么、不要做什么、怎样交付。

## 普通 subagent 与 context fork 的区别

基础阶段只需要理解一个差别：普通 subagent 更像“从当前会话派出去的独立助手”，它不应被假定自动拥有主会话里所有细节；context fork 或带 fork 语义的 skill，则更像“带着当前上下文快照去旁路执行一段流程”。

可以这样判断：

| 机制 | 更适合 |
| --- | --- |
| 普通 subagent | 独立阅读、独立审查、独立研究；你愿意在提示里明确给它材料和边界。 |
| Context fork / forked skill | 当前会话已经积累了足够背景，只是希望把一段重阅读或审查流程隔离出去。 |

即使使用 fork，也不要只写“按上面的做”。上下文快照会降低重复交代的成本，但不会替代清楚任务。好的委派仍然要明确目标、范围、输出和限制。

## 并行不是免费加速

Subagents 很容易让人产生“多开几个就更快”的错觉。并行确实能缩短等待时间，但也会放大三类风险：

- Token 和速率限制成本：多个 subagent 同时阅读大量文件，会更快消耗上下文、预算和请求额度。
- 结论合并成本：不同 subagent 可能用不同标准给出相互冲突的建议，主会话仍要负责仲裁。
- 文件冲突风险：如果多个 worker 同时编辑同一批文件，最后可能互相覆盖、重复实现或产生难以 review 的 diff。

因此，并行前要先确认任务真的独立。研究类、审查类、只读分析类任务更适合并行；会修改同一模块的实现任务，通常应先拆清文件所有权，必要时使用独立 worktree，再分别验证和合并。

对于基础读者，一个稳妥规则是：先让 subagent 只读，先返回摘要；只有当边界、验证命令和文件所有权都清楚时，才考虑让多个 agent 并行修改。

## 如何把 subagent 结果带回主线

Subagent 的产物不应该是一堆未经整理的文件摘录。主会话需要拿回的是能支持下一步行动的判断：

- 结论：回答了什么问题，推荐下一步是什么。
- 证据：读了哪些文件、日志、issue 或资料。
- 风险：哪些判断不确定，哪些地方需要人工确认。
- 影响范围：如果要修改，可能涉及哪些文件或模块。
- 验证建议：后续应该运行哪些测试、lint、typecheck 或人工 review。

让 subagent 输出这些内容，可以避免主会话重新读完全部材料。主会话负责把多个结论合并成计划，决定是否继续修改、是否补充调查、是否新建 ticket。

## 本节校验

读完 subagents 部分，你应该能做到：

- 判断什么时候用 subagent 分担大规模阅读、专业审查、并行研究或上下文隔离。
- 说明 subagent 有独立上下文，不能假设它自动知道主会话的所有背景。
- 写出包含目标、范围、输入材料、输出格式、限制条件和验证标准的委派提示。
- 区分普通 subagent 与 context fork / forked skill 的基础差异。
- 识别并行工作带来的 token、速率限制、结论合并和文件冲突风险。
- 把 subagent 的输出收束为主会话可继续行动的结论、证据、风险和验证建议。

接下来讲 hooks 和 permissions。它们解决的不是“让 Claude 更聪明”，而是“哪些事情必须被系统性地允许、询问、阻止或记录”。

## Hooks 是生命周期事件上的确定性控制

Hooks 可以理解为挂在 Claude Code 生命周期事件上的自动动作。它们不依赖模型临场判断，而是在某些工具调用或会话事件前后按规则运行。

这和 `CLAUDE.md` 的边界不同。`CLAUDE.md` 告诉 Claude “这个项目希望你怎样做”；hook 则是在具体事件发生时执行一段确定性控制。前者是行为引导，后者更接近流程护栏。

常见 hook 场景包括：

| 场景 | 适合 hook 的原因 |
| --- | --- |
| 安全阻断 | 在敏感文件、敏感目录或高风险操作发生前拦截，而不是只提醒 Claude 不要碰。 |
| 格式化 | 文件修改后自动运行项目认可的格式化步骤，减少“记得格式化了吗”的人工检查。 |
| 通知 | 长任务完成、等待人工确认、验证失败时发送本地或团队通知。 |
| 审计 | 记录关键工具调用、修改路径、审批结果或失败原因，方便复盘。 |
| 权限自动化 | 对某些低风险、重复出现的操作自动允许或拒绝，减少机械确认。 |

这些场景的共同点是：你希望它稳定发生，而不是希望 Claude “尽量记得”。如果某条规则不发生会造成安全、质量或协作风险，就应该考虑 permissions 或 hooks；如果它只是写作风格、代码偏好或团队习惯，放进 `CLAUDE.md` 或 rules 通常更合适。

## Permissions 先定义工具边界

Permissions 负责限定 Claude Code 可以使用哪些工具、命令或资源。它回答的是：

```text
这次会话里，Claude 被允许做什么？
哪些操作必须询问？
哪些操作直接禁止？
```

可以把 permissions 看成第一层边界，把 hooks 看成事件上的二次控制：

| 需求 | 更适合的机制 |
| --- | --- |
| 某类工具默认不可用 | permissions deny。 |
| 某类命令每次都要人工确认 | permissions ask。 |
| 某类低风险操作可以减少重复确认 | permissions allow，范围要窄。 |
| 工具调用前需要检查路径或输入 | `PreToolUse` hook。 |
| 工具调用后需要格式化、通知或记录 | `PostToolUse` 或其他事件 hook。 |
| 希望 Claude 选择更稳妥的工作习惯 | `CLAUDE.md`、rules 或 skill。 |

一个健康的权限策略应该从最小可用开始。先让 Claude 读项目、解释计划、运行只读检查；需要改文件时再放开编辑；需要执行命令时再限定到项目认可的验证命令。权限越宽，越需要配合人工 review、版本控制和可回滚的工作方式。

## 强制边界和提示引导不要混在一起

新手容易把三类东西写在同一个地方：

```text
项目风格应该怎样？
Claude 这次任务应该怎样做？
哪些操作绝对不能发生？
```

它们应该分开处理：

| 类型 | 适合放哪里 | 例子 |
| --- | --- | --- |
| 稳定项目引导 | `CLAUDE.md` 或 rules | 常用测试命令、目录说明、代码风格、review 标准。 |
| 可重复流程 | skill 或 slash command | 发布检查、代码审查、文档生成、ticket 实现流程。 |
| 强制执行边界 | permissions 或 hooks | 禁止编辑敏感文件、执行前询问、修改后自动格式化、记录关键操作。 |

`CLAUDE.md` 很重要，但它不是强制安全机制。它能影响 Claude 的默认行为，却不能替代权限规则或 hook 拦截。反过来，permissions 和 hooks 也不应该承载太多“请写得更清楚”“优先小步提交”这类行为建议；这些更适合放在项目记忆或 skill 中。

这个分工能让团队配置更容易 review：看到 `CLAUDE.md`，你知道它在描述工作习惯；看到 permissions 或 hooks，你知道它会实际影响工具能不能运行、某些动作是否会被自动执行。

## 基础风险：别把护栏变成新风险

Hooks 和 permissions 是安全工具，但配置不当也会制造问题。

第一类风险是 broad deny。过宽的 deny 规则可能拦掉本来安全的操作，而且不一定能靠后面更具体的 allow 规则补回来。基础阶段应先从具体路径、具体工具、具体命令类型开始，不要一上来写覆盖过大的禁止规则。

第二类风险是把 bypass permissions 当日常模式。绕过权限提示会让 Claude Code 少问很多问题，但也会移除重要的人机确认环节。它只适合隔离环境、临时实验或明确可回滚的自动化场景，不应成为真实项目里的默认工作方式。

第三类风险是 hook 副作用。Hook 可能修改文件、发通知、写日志或调用外部系统。如果多个 hook 同时匹配，某个 hook 拒绝了操作，也不代表其他已经触发的副作用一定不存在。因此有副作用的 hook 应该小、可审查、可重复运行，并尽量避免在基础项目里做复杂外部写入。

第四类风险是把 hooks 写成隐藏自动化框架。基础团队不需要一开始就建立庞大的 hook 体系。更稳的做法是先解决一两个真实痛点，例如保护敏感文件、自动格式化文档或记录高风险工具调用。等这些规则经过几轮真实任务验证后，再考虑扩展。

## 从一个最小清单开始

如果你第一次为项目设计 hooks 和 permissions，可以先用这个清单讨论，而不是直接写配置：

| 问题 | 判断 |
| --- | --- |
| 哪些文件或目录绝不能被自动修改？ | 用 permissions deny 或 `PreToolUse` hook 保护。 |
| 哪些命令应该每次询问？ | 用 permissions ask 保留人工确认。 |
| 哪些验证或格式化动作应该稳定发生？ | 考虑修改后的 hook。 |
| 哪些事件值得通知？ | 只通知会影响协作节奏的事件，避免噪音。 |
| 哪些操作需要留痕？ | 记录关键工具调用和结果，不要展开成企业审计平台。 |
| 哪些规则只是提醒 Claude 怎么工作？ | 放 `CLAUDE.md`、rules 或 skill，不放 hook。 |

这张清单的重点是先判断边界。不要为了“高级”而加 hook，也不要为了少点几次确认就放宽权限。Claude Code 的效率来自可控执行，不来自把所有护栏拆掉。

## 把 MCP、subagents、hooks 放回同一张图

这一章讲了三个进阶方向，但它们不是同一种能力：

| 问题 | 对应工具 |
| --- | --- |
| 外部事实反复复制，且需要结构化读取或受控回写 | MCP。 |
| 主上下文被大量文件、日志或研究材料塞满 | Subagents。 |
| 某些工具调用必须被允许、询问、阻止、格式化、通知或记录 | Permissions / hooks。 |

真正的成熟用法，不是“把所有高级工具都装上”，而是能说清楚这次任务的边界在哪里。缺外部事实时接 MCP；缺上下文隔离时用 subagent；缺强制控制时用 permissions 或 hooks；只是希望 Claude 保持项目习惯时，写好 `CLAUDE.md`、rules 或 skill。

进阶能力的核心不是工具百科，而是判断边界。边界判断清楚，工具会让工作流更稳定；边界判断不清，工具越多，风险和噪音也越多。

## 本章校验

读完本章，你应该能做到：

- 判断什么时候需要 MCP，而不是复制粘贴外部事实。
- 判断什么时候用 subagent 隔离大规模阅读、审查或研究。
- 解释 hooks 是生命周期事件上的确定性控制。
- 区分 permissions / hooks 的强制边界和 `CLAUDE.md` 的行为引导。
- 说出安全、质量、通知、审计和权限自动化这些典型 hook 场景。
- 识别 broad deny、bypass permissions 和 hook 副作用等基础风险。
- 把 MCP、subagents、hooks 都放回“判断边界”的工作流中。
