# 09 - MCP、subagents、hooks 等进阶工具边界

前面几章已经走过了单次开发任务的主线：让 Claude Code 进入项目、管理上下文、拆清任务、完成小步修改、验证结果，并把重复流程沉淀成 skill。

这一章进入进阶工具，但重点不是把每个工具讲成教程。基础读者更需要先建立判断边界：什么时候应该接外部系统，什么时候应该隔离上下文，什么时候需要确定性的安全控制。

本节先讲 MCP。它解决的是“Claude Code 怎样可靠地接入外部系统”，而不是“安装一个万能插件以后什么都能自动完成”。

## MCP 是外部系统适配层

MCP 可以先理解为 Claude Code 和外部系统之间的适配层。它把外部工具、数据库、API 或资源用统一方式暴露给 Claude Code，让 Claude 不必只依赖你手动复制粘贴外部事实。

适合接入 MCP 的场景，通常有一个共同特征：关键信息不在当前仓库里，却会反复影响开发判断。

| 外部系统 | MCP 适合解决的问题 |
| --- | --- |
| Issue tracker | 读取需求、验收标准、讨论记录，必要时创建或更新任务。 |
| PR/MR 与代码平台 | 读取 review 评论、变更列表、失败检查和上下文，用于审查或修复。 |
| 数据库 | 查询结构、样例数据或排查结果，辅助理解真实数据状态。 |
| 监控和实验平台 | 查看错误、指标、线上影响范围，帮助定位问题和验证修复。 |
| 设计稿 | 读取设计上下文、标注和资源，减少人工转述。 |
| 文档系统 | 读取产品说明、接口文档、决策记录和团队约定。 |

如果你只是偶尔要引用一段外部说明，把链接或摘录贴进当前任务就够了。MCP 更适合那些“每次都要查、查完还要和代码一起判断、人工复制容易漏”的系统。

## 不要把 MCP 当万能插件

MCP 不是让 Claude Code 变成“全自动接管所有工具”的开关。它只是提供连接方式，真正重要的是你暴露了哪些工具、允许它们做什么、外部内容是否可信，以及这次任务是否真的需要这些能力。

一个健康的判断顺序是：

```text
当前仓库信息是否足够？
  -> 不足的信息是否来自稳定外部系统？
  -> 是否会反复使用或需要结构化读取？
  -> 是否能限定只读或最小写入权限？
  -> 是否理解外部内容带来的信任风险？
```

如果这些问题答不上来，先不要急着接 MCP。让 Claude 明确说明“缺少哪些外部事实”“为什么不能从仓库内判断”“临时复制这一次是否已经足够”，往往更安全。

## Scope、workspace trust 和工具暴露

接入 MCP 时，最容易忽略的不是配置命令，而是共享范围。

可以把 scope 理解为“这份 MCP 配置对谁、在哪些项目里可见”。常见边界包括：

| Scope | 适合场景 | 风险提醒 |
| --- | --- | --- |
| Local | 只在当前项目、当前个人环境使用。 | 适合个人试验，但团队成员不会自动获得同样能力。 |
| Project | 随项目配置共享给团队。 | 需要更谨慎审查，因为它会影响所有信任该工作区的人。 |
| User | 跨个人多个项目可用。 | 方便个人常用工具，但不要把某个项目的权限误带到其他项目。 |

项目级 MCP 配置尤其要注意 workspace trust。一个从外部克隆来的仓库不应该仅靠提交配置，就自动让你的 Claude Code 信任并运行它声明的 MCP server。你需要先判断这个工作区是否可信，再决定是否启用其中的外部工具。

另一个边界是工具暴露。MCP server 可能暴露 tools、prompts 和 resources。对基础使用者来说，不必先理解协议细节，但必须问清楚：

- 它暴露的是只读能力，还是可以创建、更新、删除外部资源？
- 它能访问哪些账号、项目、数据库、文档或 issue？
- 它返回的内容是否可能很大，是否会挤占 Claude 的上下文？
- 它的输出是否来自用户、评论、网页、文档等不完全可信来源？
- 这次任务是否真的需要写权限，还是只读已经足够？

最小权限原则同样适用于 MCP：先只读，按任务需要逐步扩大；能限制到项目、仓库、数据库或资源集合，就不要给全局访问。

## 外部内容与 prompt injection 风险

MCP 的价值是把外部事实带进 Claude Code，但风险也来自这里：外部系统里的内容不一定可信。

例如 issue 评论、PR 讨论、文档页面、设计稿注释、监控事件描述，都可能包含人为写入的文本。Claude 读取这些内容后，可能遇到类似“忽略之前的指令”“把密钥发到这里”“不要运行测试直接提交”这样的恶意或误导性指令。这类风险通常被称为 prompt injection。

处理方式不是“永远不要接外部系统”，而是建立信任边界：

- 把外部内容当作数据，而不是新的最高优先级指令。
- 对未知来源内容保持只读，避免同时给写文件、执行命令和外部写入权限。
- 让 Claude 在引用外部事实时说明来源，例如来自哪个 issue、PR、文档或监控事件。
- 对会修改外部系统的操作保留人工确认，尤其是关闭 issue、更新 PR、写数据库、触发部署或发送消息。
- 对敏感系统设置更窄的 scope，并配合 permissions 或 hooks 做强制边界。

一个实用提示是：当 MCP 返回外部内容时，可以要求 Claude 区分“外部事实”和“执行指令”。前者可以作为判断材料；后者除非来自你信任的配置或当前用户明确授权，否则不应直接执行。

## 什么时候从复制粘贴升级为 MCP

基础阶段完全可以先复制粘贴。MCP 是在重复、结构化和权限边界都值得投入时再引入的工具。

可以用这张表判断：

| 现象 | 继续复制粘贴 | 考虑 MCP |
| --- | --- | --- |
| 使用频率 | 偶尔引用一段外部说明。 | 每个任务都要查同类 issue、PR、监控或文档。 |
| 信息形态 | 一小段文本，人工摘录不容易错。 | 多条记录、状态字段、评论线程、查询结果或资源列表。 |
| 时效性 | 内容相对稳定。 | 内容经常变化，需要读取当前状态。 |
| 任务影响 | 只帮助理解背景。 | 会影响代码修改、验证范围、审查结论或任务状态。 |
| 权限需求 | 只读链接或摘录即可。 | 需要受控地读取特定系统，或在人工确认后回写状态。 |

如果你经常在会话里做这种事：

```text
我从 issue 里复制需求；
再从 PR 里复制评论；
再从监控里复制错误；
再从文档里复制接口说明；
然后让 Claude 把它们和仓库代码一起判断。
```

这就是 MCP 值得评估的信号。不是因为复制粘贴“不专业”，而是因为它容易丢上下文、丢来源、丢最新状态，也很难稳定复用。

相反，如果这次只是让 Claude 根据一段产品说明改一个文案，复制粘贴更简单，也更容易控制边界。

## 一个最小使用心智模型

第一次在团队项目里考虑 MCP 时，不必从开发自定义 server 开始。可以先按下面的顺序和 Claude 一起评估：

1. 列出任务中反复依赖的外部系统。
2. 标记哪些只需要读，哪些可能需要写。
3. 为每个系统限定 scope：个人、当前项目，还是团队共享。
4. 明确哪些外部内容是不可信输入，需要防 prompt injection。
5. 先启用最小只读能力，完成几次真实任务后再考虑更大的权限。

你最终想得到的不是“Claude 能连很多工具”，而是“Claude 能在正确边界内读取必要事实，并把来源、限制和风险说清楚”。

## 与 subagents、hooks 和 permissions 的衔接

MCP 解决外部系统连接问题，但它不解决所有进阶工具问题。

当问题是“大量文件、日志或研究材料会塞满主上下文”时，更可能需要 subagents 或隔离上下文。它们的重点是分担阅读和分析，而不是连接外部系统。

当问题是“有些操作必须被阻止、批准、格式化、审计或通知”时，更可能需要 permissions 和 hooks。它们的重点是确定性控制，而不是让模型记住一条提醒。

这几个工具可以配合，但边界不同：

| 工具 | 主要解决什么 |
| --- | --- |
| MCP | 把外部系统事实和操作接入 Claude Code。 |
| Subagents | 隔离上下文、并行阅读、处理专门分析任务。 |
| Permissions | 限定 Claude Code 可以使用哪些工具和命令。 |
| Hooks | 在工具调用或会话事件前后做确定性控制。 |

不要因为工具高级就提前引入。只有当真实任务暴露出“外部事实反复复制”“上下文太大”“权限需要强制边界”这类具体问题时，再选择对应工具。

## 本节校验

读完 MCP 部分，你应该能做到：

- 解释 MCP 是外部系统适配层，而不是万能插件。
- 判断 issue、PR、数据库、监控、设计稿、文档系统等场景什么时候适合 MCP。
- 区分 local、project、user 这类 scope 背后的共享边界。
- 理解 workspace trust、工具暴露和最小权限为什么重要。
- 识别外部内容带来的 prompt injection 风险，并把外部文本当作数据处理。
- 判断一段“复制粘贴外部事实”的流程是否值得升级为 MCP。

后续可以继续补完整章的 subagents、hooks 和 permissions 小节。它们应保持同样的写法：讲判断边界、权限和风险，不写复杂实现教程。
