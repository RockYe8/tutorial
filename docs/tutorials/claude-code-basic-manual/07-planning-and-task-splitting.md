# 07 - Planning mode 与任务拆分

[上一章：上下文、memory 与 CLAUDE.md](06-context-memory-and-claude-md.md) | [返回目录](README.md) | [下一章：Skills 与可复用工作流](08-skills-and-repeatable-workflows.md)

上一章讲的是上下文管理：让 Claude Code 在正确的项目事实、规则和当前任务状态里工作。

这一章讲任务进入执行前的收束。很多使用 Claude Code 的失败，不是模型不会写代码，而是你把一个还没被定义清楚、风险还没暴露、上下文也装不下的任务直接推给了它。结果看起来很忙，diff 很大，最后却很难 review。

健康的任务收束大致像这样：

```text
判断任务大小和风险
  -> 小任务直接执行
  -> 中任务先调查和规划
  -> 大任务先写 spec
  -> 再拆成 fresh context 可以完成的 tickets
  -> 每个 ticket 独立执行、验证和 review
```

Planning mode 不是所有任务的仪式。它的价值，是在动手前把不确定性、风险、文件范围和验证方式摆到台面上。任务拆分也不是把工作按技术层切开，而是把一个大目标拆成一个个能交付反馈的垂直切片。

## 什么时候先 planning

如果任务满足下面任意一种情况，先规划通常比直接改文件更稳：

| 场景 | 为什么需要先规划 |
| --- | --- |
| 不确定 | 你还不知道入口文件、影响范围、现有测试或实现方案。 |
| 高风险 | 改错会影响登录、权限、账单、数据一致性、部署或生产运行。 |
| 大范围 | 需要跨多个模块、多个页面、多个服务或多个包协同修改。 |
| 架构性 | 会改变公共接口、模块边界、数据流、依赖方向或长期维护方式。 |
| 安全或数据相关 | 涉及密钥、权限、隐私数据、迁移、删除、回滚或审计。 |

你可以这样理解：直接执行适合“我知道要改什么，只需要 Claude 帮我完成”；planning 适合“我还需要 Claude 帮我判断怎么改才安全”。

例如这个请求适合直接执行：

```text
请把设置页保存成功的 toast 文案改为“设置已保存”。
只改文案，不调整触发逻辑、样式或接口。
```

这个请求则应该先 planning：

```text
请调整账号设置页的保存流程，让邮箱、密码和通知偏好可以分别保存。
先不要改文件。请先阅读相关代码，列出影响文件、实现方案、风险和验证计划。
```

第二个任务看似只是“保存流程”，但它可能涉及表单状态、API、后端校验、错误提示、测试和用户数据。直接开改很容易把范围铺大。

## Planning mode 不是拖慢小任务

把 planning mode 当成所有任务的前置仪式，会让简单工作变笨重。一个拼写修正、单行配置、文档链接、已有测试中的小断言更新，通常不需要一份正式计划。

更实用的判断是：

| 任务类型 | 推荐处理方式 |
| --- | --- |
| 小任务 | 让 Claude 定位文件、说明最小改动，然后直接执行并展示 diff。 |
| 中任务 | 先调查相关文件，给出短计划，经你确认后再修改。 |
| 大任务 | 先澄清需求并写 spec，再拆成多个 tickets，每次只实现一个。 |

小任务的重点是控制范围：

```text
请只修改这个按钮的 aria-label。
如果发现需要改其他行为，先停下来说明原因。
```

中任务的重点是先暴露影响面：

```text
请先调查搜索框 debounce 的实现位置。
输出你准备修改的文件、每个文件的改动意图、验证命令。
在我确认前不要编辑文件。
```

大任务的重点是不要让一个会话吞下全部不确定性：

```text
我们要把个人工作台升级成团队工作台。
请先把需求澄清成 spec，不要直接拆实现任务。
等 spec 稳定后，再拆成 fresh context 可以完成的 tickets。
```

## 好计划应该包含什么

一个可执行计划不只是“第一步改 A，第二步改 B”。它应该让你能在开改前判断：范围是否合理，风险是否可接受，验证是否足够，失败时怎么收住。

建议要求 Claude 的计划至少包含五类信息：

| 计划内容 | 应回答的问题 |
| --- | --- |
| 文件和模块 | 会读哪些文件、改哪些文件、为什么这些文件相关。 |
| 方案和顺序 | 先改什么、后改什么，哪些地方需要保持兼容。 |
| 风险 | 哪些行为可能被影响，哪些边界最容易漏测或误改。 |
| 验证方案 | 运行哪些测试、lint、typecheck、手工检查或截图检查。 |
| 失败处理 | 如果测试失败、发现范围变大、需求不清，应停下、回滚、换方案还是拆 ticket。 |

可以这样要求：

```text
请先进入规划，不要修改文件。

计划请包含：
- 相关文件和你判断它们相关的理由。
- 推荐方案和备选方案的取舍。
- 主要风险，尤其是数据、权限、兼容性和测试缺口。
- 最小验证命令，以及什么情况下需要扩大验证范围。
- 如果实现中发现范围超过当前任务，应该停在哪里并向我确认。
```

计划不是合同本身，但它是执行前的安全检查。真正开始改文件后，如果 Claude 发现计划里的假设不成立，应先说明偏差，而不是悄悄扩大范围。

## 从模糊任务到 spec

当任务已经大到无法用一段计划装下，就不要急着拆 tickets。需求仍然模糊时直接拆票，通常只会得到一堆看似可执行、实际互相打架的任务。

Spec 的作用，是把已经澄清的共识写成后续工作都能引用的契约。它应该回答：

- 背景：为什么要做这件事，现在的问题是什么。
- 目标：用户或系统最终要获得什么能力。
- 非目标：这一轮明确不做什么。
- 关键行为：正常路径、边界条件、错误状态和兼容性要求。
- 实现决策：已经确定的技术方向、约束和取舍。
- 验收标准：完成后怎样判断它真的满足需求。

比如“优化搜索体验”太模糊，不适合直接拆票。你至少要先澄清：

- 搜索对象是什么：标题、正文、标签，还是全部字段。
- 结果如何排序：相关性、时间、手动权重，还是现有顺序。
- 是否需要高亮、分页、空状态和错误状态。
- 性能目标是什么，是否需要后端索引或缓存。
- 本轮是否包含移动端、国际化、可访问性或埋点。

这些问题稳定后，才适合写成 spec。Spec 稳定后，review 的重心就从“需求到底是什么”转向“tickets 是否能把这份共识变成可执行反馈”。

## Ticket 是可执行反馈单元

Ticket 不是把 spec 按文件夹切成待办事项。它应该是一块能被一个 fresh context 中的 Claude Code 接住、实现、验证、review 并留下反馈的工作。

一个好的 ticket 通常包含：

| 内容 | 说明 |
| --- | --- |
| 目标 | 这一张 ticket 要交付的用户可见或系统可验证结果。 |
| 输入材料 | spec、相关研究、设计决策、已有文件或前置 ticket。 |
| 输出路径 | 允许创建或修改的主要文件、文档或 artifact。 |
| 非目标 | 明确不做哪些相邻需求，避免 scope creep。 |
| 验收标准 | 可独立检查的完成条件。 |
| 阻塞关系 | 依赖哪些 ticket，完成后解锁哪些后续工作。 |

Ticket 的大小要围绕 feedback 调整。太小会变成横向切层，交付不了可验收行为；太大又会把上下文撑爆，让 agent 在实现途中开始猜。

## Ticket review checklist

`/to-tickets` 或人工拆票之后，不要只检查“有没有很多张”。真正要 review 的，是每张 ticket 是否适合独立执行。

| 检查项 | 判断问题 |
| --- | --- |
| Vertical slice | 它是否贯穿一条完整行为链路，而不是只做 schema、只做 API、只做 UI。 |
| Tracer bullet | 它是否能先打通一条小的端到端路径，暴露真实集成问题。 |
| Blocking edges | 它是否写清楚依赖谁、阻塞谁、哪些 ticket 可以并行。 |
| Fresh context | 新会话里的 agent 只读 ticket、spec 和必要材料，是否就能开工。 |
| 独立验收 | 完成后是否能单独 demo、测试、review 或由人工验收。 |
| 过大拆分 | 如果它同时包含多个独立反馈路径，是否应该继续拆小。 |

反例是这样的：

```text
Ticket 01：新增数据库 schema。
Ticket 02：新增 API。
Ticket 03：新增 UI。
Ticket 04：新增测试。
```

这是一种横向切层。每一张都可能“做完了”，但用户到最后一张之前看不到可用行为，集成风险也会被推迟。

更好的拆法是：

```text
Ticket 01：让用户能为一条任务添加一个标签，并在任务列表显示该标签。
Ticket 02：让用户能按一个标签筛选活跃任务。
Ticket 03：让归档任务从默认列表隐藏，并提供归档入口。
Ticket 04：让归档视图也支持按标签筛选。
```

每张 ticket 仍然可能涉及数据、接口、UI 和测试，但它们都围绕一条可验收行为组织。这就是 vertical slice。第一张尤其像 tracer bullet：它不追求完整标签系统，而是先打通最小端到端路径，让真实接缝尽早暴露。

## 让任务留在 fresh context 内

Fresh context 的意思不是“没有背景”，而是“背景被压缩成可执行 artifact”。一个新的 Claude Code 会话不应该依赖你前面三小时聊天的隐性记忆；它应该能通过 ticket、spec、相关文件和必要评论重新进入状态。

当你发现下面这些信号，就该拆小或 handoff：

- Claude 需要反复重读同一批背景，仍然漏掉关键限制。
- 当前 ticket 的验收标准越来越多，已经像一个小 spec。
- 实现中频繁出现“顺便也改一下”的相邻需求。
- 验证命令无法收束，不知道到底跑哪些才算完成。
- Review 发现的不是小 bug，而是方向偏差或遗漏主要场景。

处理方式通常有三种：

- 如果需求仍然不清，回到澄清或 spec。
- 如果目标清楚但太大，回到 tickets 继续拆 vertical slices。
- 如果会话只是太长，用 handoff 把当前状态、diff、验证结果和下一步整理出来。

不要把拆小理解成降低效率。对 agent 来说，清晰的一张 ticket 往往比一个巨大任务更快完成，因为它不用在上下文里拖着全部可能性前进。

## Advanced：从澄清到 spec 再到 tickets

Matt Pocock Skills workflow 里有一条很适合进阶团队参考的链路：

```text
grill-with-docs -> to-spec -> to-tickets
```

这里的重点不是记住三个命令，而是理解三个 artifact 的关系。

`grill-with-docs` 负责带着仓库文档和领域上下文澄清需求，区分事实和需要人决定的取舍。`to-spec` 把已经稳定的 shared understanding 合成 spec，让后续实现和 review 有共同参照。`to-tickets` 再把 spec 拆成 tracer-bullet vertical slices，保证每张 ticket 能在 fresh context 中执行和验收。

这套流程适合需求复杂、团队协作多、或需要多个 agent 分批推进的工作。它不应该变成基础读者的入门门槛：小任务仍然可以直接执行，中任务仍然可以只做短计划。只有当任务大到需要共识契约和可交接反馈单元时，才值得把这条 advanced 链路完整走一遍。

## 本章小结

Planning mode 回答的是：现在是否应该先弄清楚再动手。Spec 回答的是：我们到底同意要做什么。Ticket 回答的是：下一位 agent 在一个 fresh context 里具体交付哪一块反馈。

开始任务前，可以用这张短清单收束：

- 小任务：范围清楚、风险低、验证简单，可以直接执行。
- 中任务：影响面不确定，先调查和计划，再确认执行。
- 大任务：需求或协作面太大，先写 spec，再拆 tickets。
- 好计划：包含文件、风险、验证方案和失败处理。
- 好 ticket：是 vertical slice、像 tracer bullet、有 blocking edges、能 fresh context 完成、可独立验收。

下一章会继续讲：当某类规划、验证、review 或发布流程反复出现时，怎样把它沉淀成 skill 或 slash command，而不是每次复制一段长 prompt。
