# 03 - 让 Claude Code 先读懂真实项目

[上一章：第一次启动](02-install-and-first-run.md) | [返回目录](README.md) | [下一章：完成第一次小范围修改](04-make-your-first-change.md)

上一章讲的是第一次启动：站在正确的项目目录里，先只读了解，理解权限提示和工具边界。

这一章进入真实项目阅读。目标不是让 Claude Code “把整个仓库解释一遍”，而是让它在有限上下文里建立足够准确的项目地图：这个项目做什么，重要入口在哪里，某个功能流经过哪些模块，哪些文件和当前任务真正相关，还有哪些问题没有确认。

这一步做得好，后面的改代码、调试、写测试都会更稳。做得不好，Claude 可能带着半截理解开始重构，或者把上下文窗口塞满无关文件，最后看似读了很多，实际没有形成可执行判断。

## 先从宽问题开始

进入陌生仓库时，第一轮问题应该宽，但不能空。宽问题的作用是建立项目地图，而不是马上追问某个函数。

不建议这样问：

```text
解释这个项目。
```

这句话太空。Claude 可能读到哪里算哪里，也很难知道你希望得到架构、目录、启动方式、业务流程还是代码风格。

更好的第一轮是：

```text
请先只读了解这个仓库，不要修改文件。

优先阅读 README、项目配置、项目规则文件、主要源码目录和测试目录结构。
请输出：
1. 这个项目的用途
2. 主要目录和它们的职责
3. 启动、测试、lint 或 typecheck 的入口
4. 你读过哪些文件
5. 你现在还不确定的问题

不要一次读取全仓所有文件，也不要展开生成文件、依赖目录或大型产物。
```

这个提示有三个关键点：

- 明确只读，不让阅读阶段变成修改阶段。
- 指定优先入口，让 Claude 从稳定材料开始，而不是随机扫文件。
- 要求输出“读过的文件”和“不确定点”，让理解过程可审查。

第一轮输出不需要完美。它的价值是帮你知道下一步该问哪里。

## 再把问题收窄到功能流

读完项目地图后，不要马上要求 Claude 改代码。下一步通常是把问题收窄到一个功能流、一个模块或一个开发任务。

例如你想理解登录流程，可以问：

```text
基于刚才的项目概览，请继续只读追踪登录流程。

请从路由或入口开始，沿着请求处理、认证校验、用户数据读取、错误处理和测试覆盖往下找。
输出：
1. 登录流程的步骤列表
2. 每一步涉及的文件和函数
3. 数据如何在这些模块之间流动
4. 现有测试覆盖了哪些路径
5. 哪些判断是你根据代码推断的，哪些还需要我确认

如果发现无关文件，不要继续展开。
```

从宽到窄的变化是：

```text
仓库概览
  -> 关键目录和入口
  -> 某个功能流
  -> 相关文件列表
  -> 具体函数、数据结构或测试
```

这样做能控制上下文。Claude 不需要把整个项目都塞进会话，只需要把当前任务会用到的路径读清楚。

## 让 Claude 产出可复用的阅读结果

好的项目阅读不只是“我大概懂了”。你应该要求 Claude 留下能继续使用的产物。常见产物包括架构概览、目录地图、数据流说明、术语表、相关文件列表和未解问题。

可以按任务选择输出：

| 阅读目标 | 适合的产物 |
| --- | --- |
| 第一次进入仓库 | 项目用途、目录职责、启动和测试入口、主要技术栈。 |
| 理解一个功能 | 流程步骤、入口文件、关键函数、数据流、错误路径。 |
| 准备改代码 | 相关文件列表、预期改动点、风险、最小验证命令。 |
| 准备写测试 | 现有测试位置、测试风格、缺口、可复现路径。 |
| 团队交接 | 已读文件、结论、不确定点、建议下一步。 |

例如，你可以让 Claude 输出一个相关文件列表：

```text
请把和“用户注册”相关的文件整理成表格：

- 文件路径
- 这个文件在注册流程中的角色
- 你为什么认为它相关
- 后续如果要修改注册逻辑，是否可能需要改它

只列你实际读过或通过搜索证据确认相关的文件。不要猜测。
```

也可以要求术语表：

```text
请根据你已经读过的代码整理一个术语表。

每个术语包含：
- 项目里使用的名字
- 它代表的业务概念或技术概念
- 主要出现在哪些文件
- 不要使用的近义词或容易混淆的叫法
```

术语表特别适合中大型项目。很多阅读偏差不是来自代码本身，而是来自你和 Claude 对同一个词的理解不同。

## 用流程图检查理解

当一个功能跨多个模块时，流程图比长段解释更容易发现遗漏。

你可以这样要求：

```text
请用 Mermaid 画出“创建订单”流程。

图里只放真实读到的模块、函数或服务，不要补脑不存在的组件。
每条边说明传递的数据或触发条件。
图后面列出：
1. 你读过的文件
2. 你没有继续展开的分支
3. 如果我要修改订单价格计算，下一步应该读哪些文件
```

流程图不只是为了好看。它能暴露三类问题：

- Claude 是否跳过了关键入口。
- 数据流是否断在某个模块。
- 它是否把推断当成事实。

如果图里出现你不认识的模块，先让 Claude 指回具体文件和代码位置，再决定是否继续读。

## 要求它区分事实、推断和不确定点

真实项目里，Claude 很容易把“从命名看起来像”说成“代码就是这样”。所以每次阅读输出都应要求它标明依据。

一个实用格式是：

```text
请把结论分成三类：

事实：你已经从具体文件中读到的内容。
推断：你根据命名、调用关系或项目结构推测的内容。
不确定点：还需要继续读文件或问我的问题。

每条事实后面都标出文件路径。
```

这会让你更容易审查 Claude 的理解，也能防止它在后续修改中把猜测当约束。

当不确定点很多时，不要急着全部解决。先问：

```text
这些不确定点里，哪些会影响我当前要做的登录错误提示修改？
请只继续调查会影响这个任务的部分。
```

上下文管理的重点就在这里：不是把所有背景都补齐，而是补齐当前任务需要的上下文。

## 控制文件阅读范围

新手常见误区是让 Claude “读取整个项目”。这听起来彻底，实际经常浪费上下文。

更好的做法是给阅读边界：

- 先读 README、配置、规则、目录结构和测试入口。
- 再用搜索定位关键词、路由、命令、类型名或错误信息。
- 对相关文件做深读，对无关分支只记录不展开。
- 避开依赖目录、构建产物、锁文件、大型日志、生成代码和临时文件，除非当前问题需要。
- 让 Claude 在继续扩大阅读范围前说明原因。

可以这样说：

```text
如果你认为需要继续读取更多文件，请先告诉我：
1. 你想读哪些文件
2. 为什么这些文件和当前问题有关
3. 读完后希望确认什么

在我确认前，不要扩大到无关目录。
```

这不是为了限制 Claude 的能力，而是为了把能力用在当前任务上。读代码的质量不取决于文件数量，而取决于是否读到了正确路径。

## 准备修改前的阅读收束

当 Claude 已经理解了一个功能流，准备进入修改前，先让它做一次阅读收束。

```text
在开始修改前，请先总结当前理解：

1. 当前任务真正相关的文件
2. 每个文件为什么相关
3. 你认为需要修改的最小文件集合
4. 不应该修改的文件或目录
5. 修改后应该运行的最小验证命令
6. 仍然不确定、可能影响实现的点

先不要编辑文件。
```

这个总结是第 04 章的入口。它把“读懂项目”转成“可控修改范围”。如果 Claude 说不清相关文件和验证方式，通常说明还没准备好开始改代码。

## 大规模阅读时怎么办

有些仓库很大，一个功能可能跨多个服务、多个包或多种语言。此时不要把所有阅读都塞进主会话。

基础阶段先记住两个工具思路即可：

- subagent 适合隔离大规模阅读、并行研究或专业审查。主会话只接收结构化摘要，避免上下文被搜索结果和长文件填满。
- handoff 适合在会话变长、任务要交接或上下文快失控时，把已读文件、结论、未解问题和下一步整理给后续会话。

这里不展开 subagents 的完整方法论，后面进阶章节会讲。现在你只需要知道：当阅读量本身开始压垮主会话时，应该考虑隔离阅读和总结交接，而不是硬塞更多文件。

## 应避免的误区

- 一进仓库就说“帮我优化一下”，没有先建立项目地图。
- 要求一次读取全仓所有文件，把上下文窗口消耗在无关内容上。
- 只让 Claude “解释这个项目”，却不要求读过文件、不确定点和可继续使用的产物。
- 在尚未理解入口、数据流、测试和风险时开始重构。
- 把 Claude 的推断当成事实，不要求它标明文件依据。
- 读完之后没有收束到相关文件、最小修改范围和验证命令。

## 一个完整的阅读会话骨架

下面不是必须逐字复制的模板，而是一种可模仿的节奏：

```text
第一轮：项目地图
请只读了解仓库，优先看 README、配置、项目规则、主要源码和测试目录。
输出项目用途、目录职责、启动/测试入口、读过的文件和不确定点。
不要修改文件，也不要读取生成物或依赖目录。

第二轮：功能追踪
请追踪“结账流程”，从入口到核心业务逻辑、数据存储和测试。
输出流程步骤、相关文件、关键函数、数据流和未确认问题。
只展开和结账相关的路径。

第三轮：阅读产物
请整理相关文件列表、术语表和一张 Mermaid 流程图。
事实要标文件路径，推断和不确定点单独列出。

第四轮：修改前收束
如果我要修改“优惠券校验规则”，请说明最小相关文件集合、可能风险、不应修改的文件和最小验证命令。
先不要编辑文件。
```

这四轮完成后，你就不再是在模糊地“让 Claude 看项目”，而是在建立一个可以继续执行的任务上下文。

## 本章校验

读完本章，你应该能做到：

- 让 Claude Code 先从 README、配置、规则、目录和测试入口建立项目地图。
- 把宽问题逐步收窄到功能流、相关文件、关键函数和验证入口。
- 要求 Claude 输出架构概览、目录职责、数据流、术语表、流程图或相关文件列表等读代码产物。
- 要求 Claude 明确读过哪些文件、哪些结论是事实、哪些只是推断、还有哪些不确定点。
- 控制上下文，不鼓励一次读取全仓所有文件，也不在尚未理解项目时开始重构。
- 知道在大规模阅读中，subagent 和 handoff 可以用于隔离上下文与交接摘要，但不需要在本章掌握完整方法论。
